# 01 · 定位、原则与底座

> 本文回答三个问题：deepAutoTest 是什么、它遵循什么不可让渡的原则、它站在什么技术底坐上。
> 底座部分给出**实测核实结论**，包含对前稿（`autoTestStudio` v0.3）两处错误表述的修正。

---

## 1. 定位

### 1.1 一句话

**把被测服务的源码变成可执行、可追溯、可复现的测试资产。**

### 1.2 为什么以源码为输入

| 输入 | 会怎样失效 |
|---|---|
| OpenAPI / Swagger 文档 | 文档是**手工维护的副本**，必然滞后于代码。字段漏写、约束缺失、示例过期。测试建立在文档上，等于把测试建立在别人的记忆上。 |
| 抓包 / 录制回放 | 只反映**被观察到的那些请求**。参数边界、异常分支、必填约束全部缺失。 |
| **源码** | 唯一与实现同步的真相。校验层写着 `amount ≤ 50000`，它就是 50000——不需要任何人对文档负责。 |

这就是全部理由：**源码不会说谎。**

### 1.3 核心价值链

```
源码 ──发现──► API 清单
  │                │
  ├──提炼──► 数据设计原则（边界、类型、唯一性、枚举）
  │                │
  └──采样──► 真实数据形态（来自测试库，只读 + 脱敏）
                   │
                   ▼
            fx Agent 合成用例（proposed）
                   │
              ✋ 人工确认门
                   │
                   ▼
            执行 ──► 追加式事件日志 ──► 结果投影（表 / 图 / 归档）
```

三个阶段分别回答：**测什么**（API）、**怎么算对**（原则 + 真实数据）、**跑起来是什么结果**（事件日志）。

### 1.4 与 deepStudio 的边界

**共享哲学，不共享代码。** 不复用 `moonviz` 引擎、不依赖 `.mbt.md`、不读 DDP、不调 `ddpView`。deepAutoTest 是独立 git 仓库、独立构建、独立分发。唯一的共同点是设计方法论——见 README 的哲学映射表。

## 2. 不可让渡的原则

这五条是设计红线。任何后续决策若与之冲突，以本文为准；若要修改，需走 ADR 并说明原因。

### P1 · 唯一事实源

**被测源码**是测试资产的来源真相；**追加式执行事件日志**是测试结果的真相。

以下一律**不是**事实源，只能是缓存或投影：

- 结果表 `case_result` / `step_result`
- 通过率、趋势图、慢用例榜
- 内存中的运行状态、UI 行模型
- 应用侧的 `Cmd.persist()` 快照
- 导出的报告文件（PDF / HTML / JSON）

**推论**：任何投影丢失都可以从事件日志重建。任何"因为表里有所以算数"的设计都是错的。

### P2 · 派生不存储

Native SDK 的官方立场是 *derive, don't store*：计算值在视图期派生，不落 Model。deepAutoTest 把它提升为结果层原则：

- 通过率 = `count(verdict=passed) / count(*)`，**视图期算**，不存字段
- 耗时分位、慢用例榜、不稳定识别 = **查询期算**，不存聚合表
- 只有"原始观测"落库：状态码、耗时、报文、断言的实际值

**推论**：不允许出现"预先聚合的统计表"作为第二真相。聚合永远是从事件/结果算出来的。

### P3 · 改变真相必须过门

三类对象遵循同一状态机：`proposed → adopted | rejected`。**AI 生成 ≠ 生效。**

适用对象：API 候选（低置信度）、数据设计原则、测试用例。

- Agent 只能产出 `proposed`
- 人工采纳 / 修改 / 拒绝是终态
- 每次裁决留痕：谁、何时、从什么改成什么

**推论**：不存在"AI 直接写进用例库"的路径。放宽只允许是**项目级显式开关**、默认关、可审计。

### P4 · 一切可回放、可重判

事件日志 append-only、有单调序号。由此获得三个能力：

1. **重放**：不重新执行，就能重建当时的界面与结论
2. **重判**：判定规则变了，对历史运行重新计算 verdict，数据不动
3. **对账**：两次运行做 diff，回答"是代码变了还是环境变了"

**推论**：判定逻辑必须与采集逻辑**分离**，且判定必须是纯函数。

### P5 · 项目即边界

`projectId` 是最高层作用域。源码索引、API、原则、环境、数据库连接、用例、运行、Agent 会话，全部挂 `projectId`，**物理与逻辑双隔离**。

- Agent 工具强制 `pid` 首参，越界读写直接拒绝并留痕
- Agent 上下文装配只取当前项目，系统提示词中不出现其它项目任何信息
- 跨项目只允许**统计聚合**（只读仪表盘），不允许发生合成或检索
- 原则/环境不自动跨项目复用；提供显式"复制到项目"操作，且生成 `proposed` 副本走人工复核

**推论**：领域层函数签名以 `ProjectScope` 为第一参数，隔离在编译期即被约束。

## 3. 技术底座

> **本节已由 [10-技术选型.md](10-技术选型.md) 取代。**
> 前一版基于 Native SDK + libfx 的选型已废弃——原因是它为了"原生感"牺牲了本产品最核心的能力（源码 AST 分析、数据库驱动、Agent），最终不得不引入 Node 边车，付出四层架构的代价。
> 新版选型：**系统 WebView 壳 + 内置 Node（主线程 + Worker 池）+ React**。完整推导见 10。
>
> 下方保留对两个底座的**实测核实结果**，作为"为什么不用"的证据记录——这些是真实核实过的，不是猜测。

### 3.1 libfx —— 真实，且贵方已在用（仍然采用）

| 项 | 核实结果 |
|---|---|
| 包 | `libfx`，npm 最新 `0.0.10`（2026-09-14 仍在更新） |
| 来源 | `vercel-labs/fx` 仓库的 `sdk/` 目录 |
| 描述 | "Embed fx agents and terminals in JavaScript hosts" |
| 形态 | **N-API 原生模块**（`libfx.darwin-arm64.node` 等），另有 Wasm + JSPI 后端 |
| 运行要求 | **Node.js 20+**；Wasm 后端需 JSPI 能力的运行时 |
| 真实 API | `createFxAgent({ apiKey, model, instructions, tools, checkpoint, backend })` |
| 会话操作 | `prompt` / `checkpoint` / `close` 三件套 |
| 持久化归属 | **宿主拥有持久化**——checkpoint 只含对话历史与用量，恢复时须重新注入 model / credentials / instructions / tools |
| 实测痕迹 | `deepStudio/deepDesign/agent/fx-agent.mjs` 已在用 `libfx.createFxAgent` |

**结论**：libfx 继续采用。**关键在于它需要 Node**——这正是新版必须内置 Node 运行时的重要原因之一。此外它不能跑在最外层（webview 主线程事件循环被 `show()` 占用），需在 Worker 或子进程中运行。

### 3.2 Native SDK —— 真实，但**不采用**

| 项 | 核实结果 |
|---|---|
| 站点 | `native-sdk.dev`，Vercel Labs 出品，Apache-2.0，**pre-1.0（API 仍在动）** |
| 标记语言 | 官方名 **Native markup**，文件 `.native`（不叫 htmlx） |
| 逻辑语言 | TypeScript（默认 `src/core.ts`）或 Zig |
| 运行时 | Zig 引擎直绘，**二进制内无浏览器 / 无 WebView / 无 JS 运行时** |
| 组件目录 | 真实存在，约 45+ 组件（`table` / `tree` / `virtual list` / `timeline` / `chart` / `code` / `split` / `status bar` 等） |
| SQLite | 有（引擎拥有的 `app.db`，迁移 + 命名查询） |
| 自动化服务器 | 有（快照 / 驱动控件 / 断言 / 确定性截图 / 录制回放） |

**它是真实且成熟的**——问题不在质量，而在**与本产品需求的错配**：

| 错配点 | 后果 |
|---|---|
| **TS core 是闭子集**（禁 JSON / 正则 / async / npm / `Map` / `string` 字段） | 源码分析、数据库驱动、HTTP 执行、Agent 编排**全部写不进去**，必须外挂边车 |
| **二进制内无 JS 运行时** | libfx（N-API）无法加载，必须常驻 Node 子进程 |
| pre-1.0 | 长期维护成本 |

**最讽刺之处**：为了"不需要 Node"而选它，结果因为核心能力都在 Node 生态，反而**必须**额外挂 Node 边车——比直接用 Node 多了一层 IPC 与两套契约。

**正确的判断**：deepStudio 选它是合理的（视觉编辑器，界面即产品，原生渲染是核心价值）；deepAutoTest 选它是错的（测试工具，价值在分析准确性与结果可信度，界面是容器）。**共享哲学，不必共享栈。**

### 3.3 实测发现的五条硬约束（记录备查）

这些是核实 Native SDK 时发现的具体限制，记录在此以免将来重蹈：

| 约束 | 影响 |
|---|---|
| TS core 禁 `JSON` / 正则 / `async` / `Promise` / npm / `Map` / `Set` | 领域逻辑无法在 core 内实现 |
| 禁 `string` 类型 Model 字段（NS1024），文本一律 `Uint8Array` | 所有文本需手动字节化与解码 |
| `Cmd.fetch` 响应体上限 **256 KiB**、请求体 64 KiB、header ≤8 且 ≤1 KiB | **不能作为测试执行引擎** |
| `Cmd.db.query` 单次结果上限 **8192 行 / 8 MiB**；`exec` ≤64 语句一事务 | 结果表必须分页；投影写入必须攒批 |
| 订阅面极窄：仅 `Sub.timer` + `Sub.q<Name>`（`:live` 查询） | 无通用流式订阅，实时方案需绕道 SQLite |

**这些约束是本产品放弃该栈的直接原因**——它们并非缺陷（对视觉编辑器完全够用），而是与"测试工作台 + 源码分析"的需求不匹配。

### 3.4 新版选型的一句话理由

> **内置 Node（拿到 AST / 数据库驱动 / Agent 生态），UI 用系统 WebView（不捆绑 Chromium，体积减半）。**

详见 [10-技术选型.md](10-技术选型.md)。

## 4. 与前稿（v0.3）的差异总览

| 前稿 | 本稿 | 原因 |
|---|---|---|
| 名 `autoTestStudio` | **`deepAutoTest`** | 命名统一，强调独立项目 |
| UI 框架称 htmlx | 官方名 **Native markup**（但最终未采用该栈） | 官方名；避免检索与 AI 生成对不上 |
| **技术栈：Native SDK + libfx 边车** | **系统 WebView + 内置 Node + React** | 见 §3 与 [10](10-技术选型.md)：前一版为"原生感"牺牲了 AST/驱动/Agent 生态 |
| 架构四层（含 service host + Node 边车） | **两层（主进程 / 渲染进程）** | 主进程即 Node，边车与 IPC 协议整体消失 |
| Agent 同进程内嵌（后又改为边车） | **Worker 内或独立子进程运行 libfx** | 外层主线程事件循环被 `show()` 占用，且需隔离 Agent 崩溃 |
| Agent 工具带 pid 首参 | **pid 降级为会话常量**（结构性防越权） | 见 [07 §3.2](07-Agent与人机门.md#32-越权防护的实现层次) |
| S6「执行与归档」一段 | **拆成完整的 03 测试流程 + 04 结果模型 + 05 结果呈现** | 本稿重点，前稿过薄 |
| 结果即"留痕三件套" | **事件日志为真源 + 判定纯函数 + 投影 + 重判 + 对账** | 让"可回放"落地为可操作能力 |
| 实时输出靠"流式事件驱动面板" | **IPC 推送 + 增量应用 + 定期对账** | 栈变更后无需绕道 SQLite |
| 六阶段管线 | 保留 S1–S6，但 **S6 内部展开为 Run 生命周期** | 流程不变，深度增加 |

**未变的部分**（经核实无需修改，且与栈无关）：五条原则 P1–P5、项目一级隔离域、`projectId` 贯穿、三类对象状态机、六阶段管线与三处人工门、SSRF 分档策略、只读采样四层、写时脱敏、事件日志/判定纯函数/重判/对账、verdict 六态与三条结果可信纪律、源码为输入的核心判断。
