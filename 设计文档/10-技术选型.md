# 10 · 技术选型

> **本文从产品需求反推技术栈**，不沿用任何既有平台的栈。
> **当前结论：系统 WebView 壳 + 内置 Node，架构为主线程 + Worker 池。**
>
> 本文的关键判断都附有**本机实测证据**（macOS 26 / Node 20.19 / Apple Silicon），不是推测。

---

## 1. 需求强度排序（选型的驱动力）

| 级别 | 需求 | 说明 |
|---|---|---|
| **S 级** | **分析 TS/JS 源码**（AST 级：路由、校验规则、Prisma schema） | 产品的定义性能力。做不了这个，产品不存在 |
| **S 级** | **真实 HTTP 执行**（任意 header/body 大小、自签证书、重定向追踪） | 测试执行是另一半定义 |
| **A 级** | 多数据库只读采样 + 驱动级控制（MySQL/PG/SQLite 原生驱动） | S4 阶段依赖 |
| **A 级** | AI Agent 集成（工具调用、流式输出、会话续跑） | S5 阶段依赖；libfx 是现成选择 |
| **A 级** | **分发体积要小** | ★ 本次新增硬约束。Electron 的 ~124 MB 被判定**过重** |
| **B 级** | 大表格实时呈现（数百至数千行，实时追加） | 结果呈现主体 |
| **B 级** | 跨平台（macOS 优先） | 分发需求 |
| **C 级** | "原生感"（启动快、无浏览器痕迹） | 加分项 |

**两个 S 级需求 + 一个 A 级（体积）共同决定了本文结论。**

### 1.1 不变的关键洞察

**S/A 级功能需求全部指向 Node 生态**：`ts-morph`（AST）、`undici`（HTTP）、`mysql2`/`pg`（数据库）、`libfx`（Agent）都是 Node 包。

**因此后端必须是 Node。** 这一条从上一版沿用，未变。

### 1.2 本次新增的约束：体积

| 方案 | 分发体积（macOS arm64） | 备注 |
|---|---|---|
| Electron 44 | **~124 MB（压缩包），解压后更大** | 捆绑完整 Chromium |
| **系统 WebView + Node** | **~46 MB（Node 压缩）+ 9.3 MB（原生插件）** | ★ 本文方案 |

**结论：去掉 Chromium，UI 用系统自带的 WebView。**

## 2. 决策一：UI 壳用系统 WebView（不捆绑浏览器）

### 2.1 候选淘汰过程

| 方案 | 后端 | UI | 体积 | 结论 |
|---|---|---|---|---|
| Electron | Node ✅ | 捆绑 Chromium | ~124 MB ❌ | **本次排除**（体积） |
| Tauri | **Rust** ❌ | 系统 WebView | ~10 MB | **不考虑**（用户明确排除；后端是 Rust，会丢掉 Node 生态） |
| Neutralinojs | **自有运行时** ❌ | 系统 WebView | 小 | 后端不是 Node，无法 `require('libfx')` / `ts-morph` |
| Electrobun | Bun / 自有 JSC ❌ | 系统 WebView | 小 | 后端不是 Node，N-API 兼容性未知 |
| **native webview 绑定** | **Node ✅** | **系统 WebView ✅** | **小 ✅** | ★ **采用** |

**淘汰的共同逻辑**：凡是"后端不是 Node"的方案（Tauri / Neutralino / Electrobun），都会丢掉本产品最重要的 S/A 级能力。**不能为了体积牺牲生态。**

**唯一同时满足"系统 WebView + Node 后端"的，就是把系统 WebView 直接绑定进 Node 进程。**

### 2.2 为什么现在可行

这类绑定依赖一个古老的 C 库 **`webview`**（WebKit/GTK/Edge 的极简封装）。过去用它做产品的障碍，现在大多消失：

| 历史问题 | 现状 |
|---|---|
| 需用户本地编译 | 仍需编译，但**实测 10 秒完成**（§2.4）；可 CI 预编译随包分发 |
| 缺 TypeScript 类型 | ✅ 有完整 `.d.ts`（含 JSDoc） |
| 只有 C 接口 | ✅ 有 `Webview` 类，`bind` / `eval` / `dispatch` / `init` 等高层 API |
| 无 IPC | ✅ `bind(name, fn)` 提供双向调用（含异常传播） |

### 2.3 ★ 实测发现的硬约束：`show()` 阻塞 Node 事件循环

**这是本方案最重要的一条约束，整个架构围绕它设计。**

实测（`probe2.mjs`）：调用 `show()` 后，**主线程的 `setInterval` 不触发、`fetch` 不执行、`await` 不完成**。

```
[  125ms] 调用 show() 之前
（此后无任何日志 —— 定时器未触发、fetch 未执行）
```

官方文档也确认："This will block the thread. Functions like `setInterval` won't work."

**原因**：`show()` 进入系统 WebView 的**原生主循环**（Cocoa run loop），Node 事件循环被完全占用。

**含义（关键）**：**所有异步 IO 都不能在主线程做**，包括 HTTP 执行、数据库查询、AST 分析、libfx Agent 调用。

### 2.4 ★ 实测验证的解法：Worker + SharedArrayBuffer + Atomics

实测（`probe5.mjs`）：

```
worker 就绪: wait=ok ctrl0=100        ← 主线程阻塞后，worker 仍活着
调用 show()
页面: 第1次: pong-from-worker          ← ★ 13 次真实 HTTP 请求全部成功
页面: 第2次: pong-from-worker
...
页面: 第13次: pong-from-worker
```

**架构**：

```
┌──────────────────────────────────────────────────────────────┐
│ Node 主线程（只有 UI 壳，不做任何 IO）                          │
│  · Webview 实例（系统 WebView 窗口）                           │
│  · w.bind('rpc', ...) 收页面调用                               │
│  · show() —— 阻塞在此，运行原生主循环                           │
└───────────────┬──────────────────────────────────────────────┘
                │ postMessage + SharedArrayBuffer + Atomics
                │ （跨线程，不依赖被阻塞的事件循环）
┌───────────────▼──────────────────────────────────────────────┐
│ Worker 线程池（★ 全部 IO 与重计算）                             │
│  · HTTP 执行（undici）        · 数据库采样（mysql2/pg）         │
│  · AST 分析（ts-morph）★ CPU 密集                              │
│  · 断言沙箱（可强制终止）      · libfx Agent                   │
│  · SQLite 读写                 · 本地静态服务（供 WebView 加载）  │
└──────────────────────────────────────────────────────────────┘
```

**为什么必须用 `SharedArrayBuffer` + `Atomics`**：普通 `postMessage` / `on('message')` 依赖事件循环**回调**，而主线程事件循环被 `show()` 占用了。实测（`probe6.mjs`）：

- **`async` 的 `bind` 回调也会挂起**（日志停在 `asyncCall(2) 开始`，Promise 永不 resolve）
- 主线程内的 Promise / 定时器全部失效

**`Atomics.wait` 是同步阻塞等待**，不依赖事件循环，因此能在被占用的主线程里工作：

```js
// 主线程（在 bind 回调内，被 show() 的原生循环同步调用）
w.bind('rpc', (_wv, reqJson) => {
  const { method, params } = JSON.parse(reqJson);
  writeRequest(sharedBuf, method, params);        // 写入共享内存
  Atomics.store(ctrl, 0, REQ_READY);
  Atomics.notify(ctrl, 0);
  Atomics.wait(ctrl, 1, WAITING, 30000);          // ★ 同步等待 worker
  return readResponse(sharedBuf);                  // 读回结果
});
```

**worker 侧有自己完整的事件循环**，`fetch` / 数据库 / AST 全部正常（已实测）。

**这是一处真正的架构发现**：若没实测到"`show()` 阻塞事件循环"，会写出"打开窗口后所有请求都超时"的应用，且极难定位。

### 2.5 `bind()` 提供的能力（已实测）

| 能力 | 状态 |
|---|---|
| Node ↔ 页面双向调用 | ✅ `bind(name, fn)` / 页面 `await window.name(...)` |
| 参数与返回值 | ✅ 自动 JSON 序列化（多参数、对象） |
| **异常传播** | ✅ Node 侧抛错 → 页面侧 Promise reject |
| 页面注入初始化脚本 | ✅ `init(js)`，在 `window.onload` 前执行 |
| 页面执行 JS | ✅ `eval(js)`（单向，不取返回值） |
| 多窗口 | ✅ 每个 `new Webview()` 一个窗口 |
| DevTools | ✅ `new Webview(true)` |
| **`async` bind** | ❌ **会挂起**（事件循环被占）——RPC 必须写成同步 + `Atomics.wait` 形式 |
| 页面自身 `fetch` | ⚠️ 可用，但受系统 WebView 的 CORS 约束 |
| 原生菜单 / 托盘 / 通知 / 文件对话框 | ❌ 未提供（见 §2.7） |

**前端资源加载**：起一个仅监听 loopback 的本地静态服务，`Webview.navigate('http://127.0.0.1:PORT')`。这比 `html()` 内联全部资源更实际（支持相对路径、source map）。

**⚠️ 实现陷阱**：主线程事件循环被 `show()` 占用，**本地静态服务必须在 worker 里起**——否则页面根本加载不出来。这是不注意就必然踩的坑。

### 2.6 页面侧网络能力

系统 WebView（macOS WebKit）自身有网络栈，页面里的 `fetch` 可用（受 CORS 限制）。对本产品是**有价值的补充**：

- 前端可直接拉取**不需要凭据**的资源
- 但**测试执行绝不能走页面 fetch**（需任意 header、自签证书、无 CORS 限制）——仍走 worker 里的 undici

### 2.7 明确的缺口与补法

`webview` 库很薄，**不提供**原生菜单、托盘、通知、文件对话框：

| 缺口 | 补法 |
|---|---|
| 文件选择/保存 | **HTML `<input type="file">`**（WebView 支持，够用）或 Node 侧平台 API |
| 原生菜单栏 | 需 ObjC 桥接（`unsafeWindowHandle` 给了 `NSWindow` 指针，可自行扩展）；**初版省略，用应用内 HTML 菜单** |
| 系统通知 | `node-notifier`（跨平台，成熟） |
| 托盘图标 | 需平台特定模块；**初版省略** |
| 剪贴板 | 页面 `navigator.clipboard` |
| 自动更新 | 自写（检查 + 下载 + 替换） |

**判断**：这些缺口对本产品**不阻断**——deepAutoTest 是测试工具，不依赖托盘/原生菜单。**用应用内菜单替代原生菜单栏是可接受的取舍**，换来约 80 MB 的体积节省。

## 3. 决策二：Node 的内置与分发

### 3.1 体积实测

| 项 | 体积 |
|---|---|
| Node 22 darwin-arm64（官方 tar.gz） | **46 MB（压缩）** |
| Node 20 本机二进制（含全量 ICU，未压缩） | 85 MB |
| 原生 webview 插件（编译后） | 9.3 MB |
| 前端产物（React + Vite，gzip） | ~1 MB |
| **合计（估）** | **~55–70 MB** |

对比 Electron 44 的 **~124 MB（压缩包）**——**约为其一半**，且解压后差距更大（Electron 含完整 Chromium）。

**进一步压缩空间**：Node 官方的 `small-icu` 构建可省约 20 MB；`--experimental-sea-config`（Single Executable Application）可把 JS 打进二进制；剥符号表。

**建议**：初版用官方 Node 二进制 + SEA 打包；若体积仍不满意，M6 再评估 small-icu。

### 3.2 Node 版本：必须 22+

原因：`node:sqlite` 内置模块需 22+（本机 20.19 实测 `ERR_UNKNOWN_BUILTIN_MODULE`）。

**但 `node:sqlite` 是可选优化**：若用 22+ 且功能够用，可省掉 `better-sqlite3` 的原生依赖；若不够，用 `better-sqlite3`（在 worker 里跑，**同步 API 正好合适**——worker 本就要阻塞等待）。

### 3.3 libfx 必须在 Worker 或子进程中（★ 待验证 W1）

libfx 是 N-API 原生模块，需 Node 20+。**它不能在主线程跑**（网络 + 流式，而主线程事件循环被占用）。

两条路径，按优先级：

| 方案 | 说明 | 风险 |
|---|---|---|
| **① worker_threads 里 `require('libfx')`** | Node 允许 worker 加载 addon | 中（N-API 在 worker 的兼容性、checkpoint 二进制跨线程传递需实测） |
| **② 独立 child_process** | 子进程有完整事件循环，完全不受 `show()` 影响，且天然隔离（Agent 崩溃不影响 UI） | 低（更稳妥，代价是 stdio IPC，但只有 Agent 一路） |

**②是天然的兜底**：即使 worker 方案失败，退到子进程仍可行。**这让 W1 的风险可控。**

## 4. 决策三：各层具体选型

### 4.1 UI 壳

| 用途 | 选型 |
|---|---|
| 窗口 + WebView | **`webview-nodejs`**（0.5.0，底层 `libwebview-nodejs` 0.12.2） |
| 加载前端 | 本地 loopback 静态服务（**在 worker 中**）+ `navigate()` |
| 应用内菜单 | HTML + Radix DropdownMenu（替代原生菜单栏） |

### 4.2 界面框架

| 用途 | 选型 | 理由 |
|---|---|---|
| 框架 | **React 19** | 生态最全（虚拟表格、图表、代码查看器都首选 React） |
| 构建 | **Vite** | 最快；产物小 |
| 虚拟表格 | **`@tanstack/react-virtual`** | 万行无压力 |
| 状态 | **Zustand** | 轻量够用 |
| 样式 | **Tailwind CSS** + CSS 变量 | 深色主题用变量；快速迭代 |
| 图表 | **uPlot**（趋势）+ **recharts**（分布/构成） | uPlot 极小极快 |
| 代码展示 | **Shiki** 或 **CodeMirror 6** | 可折叠、可搜索 |
| 无样式原语 | **Radix UI** | a11y 基础 + 样式自控 |
| 命令面板 | **cmdk** | 事实标准 |
| Markdown（Agent 输出） | `react-markdown` + `rehype-sanitize` | **必须 sanitize**（不可信输入） |

### 4.3 主进程 / Worker 侧

| 用途 | 选型 | 理由 |
|---|---|---|
| **源码分析** | **`ts-morph`**（主）+ `oxc-parser` / `@babel/parser`（辅） | 类型级分析能力独占（zod/Prisma 约束解析） |
| **HTTP 执行** | **`undici`**（Node 内置） | 流式、无大小限制、per-request dispatcher（自签证书按环境配） |
| DB 驱动 | `mysql2` / `pg` / `better-sqlite3`（或 Node 22 `node:sqlite`） | 四层只读防护可在驱动层强制 |
| 本地存储 | SQLite（worker 内） | 事件日志 append-only |
| **Agent** | **`libfx`**（worker 内，或降级到 child_process） | 现成选择 |
| 断言沙箱 | `node:vm` + 独立 Worker（可 `terminate()`） | `vm` 非安全边界，需 worker 兜底 |
| 并发桥 | **SharedArrayBuffer + Atomics** | §2.4 |

### 4.4 ★ 凭据存储是个真实缺口

脱离 Electron 后没有 `safeStorage`（走 Keychain/DPAPI/libsecret）。替代方案：

| 平台 | 方案 |
|---|---|
| macOS | 调 `security` 命令行（Keychain）：`security add-generic-password` / `find-generic-password` |
| Windows | `wincred` 的 N-API 绑定，或 `keytar`（已归档但可用） |
| Linux | `libsecret` 绑定，或 `secret-tool` 命令行 |
| **兜底** | 自写加密文件（AES-256-GCM），主密钥由用户口令经 Argon2id 派生 |

**纪律**：**必须诚实告知保护级别**。若用口令保护，界面上要明说"这些凭据受口令保护，不是系统钥匙串"——不能假装等同。这与 [08 §5.4](08-安全基线.md) 的"不静默降级"同源。

### 4.5 测试与打包

| 用途 | 选型 | 备注 |
|---|---|---|
| 单元测试 | **Vitest** | — |
| 界面测试 | **Vitest + Testing Library** | ⚠️ **放弃浏览器级 E2E**（见下） |
| 跨层集成 | 通过 `bind` 注入测试驱动 | 覆盖页面↔Node 的 RPC |
| 打包 | 自写脚本（Node 二进制 + 原生插件 + 前端产物 + `better-sqlite3`） | → dmg / zip |
| 更新 | 自写（检查版本 + 提示下载） | 初版不做静默替换 |

**E2E 的降级必须说明**：Electron 下可用 Playwright 驱动；系统 WebView **没有标准自动化协议**（macOS WebKit 有 Safari 的 WebDriver，但配置复杂且不通用）。因此界面测试降到**前端层**（组件测试）+ 通过 `bind` 注入的集成测试。**这是本方案可接受的代价之一**，但要在 M1 就明确，不能等到 M5 才发现无法做 E2E。

## 5. 新架构（三层，两个进程）

```
┌──────────────────────────────────────────────────────────────────┐
│ ① Node 主线程（UI 壳，无 IO）                                      │
│     Webview 窗口 · bind RPC 路由 · show() 阻塞于此                  │
└────────────────────────────┬─────────────────────────────────────┘
                             │ 页面 ↔ Node：webview bind（自动 JSON）
                             │ 主线程 ↔ Worker：SAB + Atomics（同步）
┌────────────────────────────┴─────────────────────────────────────┐
│ ② Worker 池（全部 IO 与计算）                                      │
│     领域层：source / adapters / principles / sampler / runner    │
│             / judge / agent / urlguard                           │
│     存储层：SQLite（事件日志 / 投影 / 项目域）                       │
│     服务层：本地 loopback 静态服务（供 WebView 加载前端）             │
└────────────────────────────┬─────────────────────────────────────┘
                             │ loopback HTTP
┌────────────────────────────┴─────────────────────────────────────┐
│ ③ 系统 WebView（渲染进程）                                         │
│     React 界面 · 通过 window.rpc.* 调用 Node                       │
│     ⚠ 无 contextIsolation/nodeIntegration 开关                   │
│        → 隔离靠"不给页面任何 Node 能力"（无桥即无权限）                │
└──────────────────────────────────────────────────────────────────┘
```

**与 Electron 版对照**：

| 维度 | Electron 版 | 本方案 |
|---|---|---|
| 分发体积 | ~124 MB+ | **~55–70 MB** |
| 渲染引擎 | 捆绑 Chromium（版本自控） | **系统 WebView**（版本随 OS） |
| 主进程 IO | 正常（事件循环可用） | **必须走 Worker**（`show()` 阻塞） |
| IPC | Electron IPC（成熟） | **webview `bind` + 手工路由** |
| 隔离 | contextIsolation + sandbox | **页面天然无 Node 能力** |
| 原生菜单/托盘 | 内置 | **缺失，需自己补或省略** |
| 自动更新 | electron-updater | **自写** |
| 凭据 | safeStorage | **平台 CLI / keytar / 自写加密** |
| E2E 测试 | Playwright 可驱动 | **降到前端测试** |
| 跨平台一致性 | 高（Chromium 统一） | **低**（WebKit / WebView2 / GTK-WebKit） |

### 5.1 收益与代价（诚实对照）

**收益**：

1. **体积减半**（124 MB → ~60 MB）
2. **页面天然无 Node 能力**——没有 `nodeIntegration` 开关可以配错，隔离是结构性的
3. 启动更快、内存更低（复用系统 WebView）

**代价**：

| 代价 | 严重度 | 说明 |
|---|---|---|
| **所有 IO 必须走 Worker + SAB/Atomics** | 中 | 架构复杂度上升，已实测可行 |
| **跨平台渲染差异** | **中** | macOS WebKit / Windows WebView2 / Linux GTK-WebKit 行为不同 |
| **E2E 自动化降级** | 中 | 无法用 Playwright 做浏览器级测试 |
| **上游维护风险** | **中** | `webview` 是小型开源项目，需评估长期维护 |
| 原生菜单/托盘缺失 | 低 | 应用内菜单替代 |
| 自动更新需自写 | 中 | 无成熟方案 |
| 凭据存储需自写 | 低 | 平台 CLI 或口令保护 |

## 8. 风险与对策

| 风险 | 概率 | 影响 | 对策 |
|---|---|---|---|
| **W1 失败：libfx 无法在 worker 加载** | 中 | **高** | **退到独立 child_process**（完整事件循环，不受 `show()` 影响，天然隔离） |
| **上游 `webview` 停止维护** | 中 | 中 | 自写 N-API 绑定（库很薄，约数百行）；或用 `webview_deno` 的 C 层 |
| **跨平台 WebView 差异** | **高** | 中 | 前期只支持 macOS；Windows/Linux 列入 M6 并实测（W6） |
| SAB 桥调试困难 | 中 | 中 | 统一封装成 RPC 层，业务代码不感知；加详细日志 |
| 自写更新器不可靠 | 中 | 中 | 初版只做"检查新版本 + 提示下载" |
| 用户需装 cmake 才能构建 | 中 | 低 | **仅开发需要**；分发包用 CI 预编译插件（W7） |

**W1 的兜底值得强调**：即使 worker 方案失败，**退到 child_process 是自然的**——子进程有完整事件循环，完全不受 `show()` 阻塞影响，且天然隔离。代价是 Agent 一路走 stdio IPC，量很小。**这让 W1 的风险可控。**

## 9. 一句话总结

> **去掉 Chromium，UI 用系统 WebView，后端是内置 Node —— 体积从 ~124 MB 降到 ~60 MB。**
>
> 代价：Node 主线程被 `show()` 的原生主循环占用，**所有 IO 必须走 Worker**（已实测用 SAB + Atomics 可绕过）；原生菜单/托盘/自动更新需自补或省略；跨平台渲染有差异；E2E 自动化降级。
>
> 换来：体积减半、页面天然无 Node 权限（隔离是结构性的而非配置的）、启动更快。

**与 deepStudio 的关系不变**：deepStudio 是视觉编辑器（界面即产品，原生渲染是核心价值）；deepAutoTest 是测试工具（分析准确性与结果可信度是核心价值，界面是容器）。**共享哲学，不必共享栈。**
