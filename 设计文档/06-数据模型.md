# 06 · 数据模型与持久化

> 本文把 [03 流程](03-测试流程.md)与 [04 结果模型](04-结果模型.md)落到 **SQLite**（`node:sqlite` 优先，必要时 `better-sqlite3`）上。
> 技术选型见 [10](10-技术选型.md)，主进程结构见 [02](02-架构.md)。
> 所有表名/字段名与 03/04 的领域模型一一对应。
>
> **注意**：前一版因使用 Native SDK 的引擎内嵌 SQLite，存在若干硬约束（STRICT 表、单次结果 8192 行 / 8 MiB、exec ≤64 语句一事务、生命周期 PRAGMA 被拒）。**改用自管 SQLite 后这些约束全部消失**，但下文保留相关讨论作为设计参考（分页与攒批虽不再是硬性要求，仍是良好实践）。

---

## 1. 迁移纪律

### 1.1 只增不改

```
src/schema/0001_init.sql
src/schema/0002_run_events.sql
src/schema/0003_artifacts.sql
...
src/schema/migrations.lock.json     # 生成物，必须提交
```

**四条硬规则**（团队纪律，违反会导致数据事故）：

| 规则 | 说明 |
|---|---|
| 文件名 `NNNN_name.sql`，编号连续 | 官方要求 append-only、contiguous |
| **已发布的迁移编号不得编辑或复用** | 改了会导致已有库的 checksum 不符 |
| 表用 `STRICT` | 官方推荐，类型严格；避免 SQLite 的动态类型陷阱 |
| 用 CLI 或脚本生成编号（`scripts/new-migration.ts`） | 不要手写编号，避免冲突 |

**为什么"只增不改"对测试工具特别重要**：用户的历史运行数据是不可再生资产（当时的环境、当时的代码）。迁移事故会让他们永久失去这些数据。宁可多写几个迁移，不可改历史迁移。

### 1.2 破坏性变更的正确做法

需要改列时（而非加列）：

```
① 新迁移中 ALTER TABLE ADD 新列
② 数据回填（UPDATE ... SET new_col = ...）
③ 保留旧列一段时间（标记 deprecated，不删）
④ 后续迁移再考虑 drop（SQLite 的 DROP COLUMN 有限制，可能需要重建表）
```

**不做破坏性变更**，因为测试数据的历史完整性优先于 schema 整洁。

## 2. 表结构

### 2.1 项目域（P5 隔离的根）

```sql
-- name: 0001_init.sql

CREATE TABLE project (
  id            INTEGER PRIMARY KEY,
  name          TEXT    NOT NULL,
  source_type   TEXT    NOT NULL,          -- git | local | zip
  repo_url      TEXT,                      -- SSRF 校验后存储
  local_path    TEXT,
  git_ref       TEXT,
  status        TEXT    NOT NULL,          -- active | archived
  created_at_ms INTEGER NOT NULL,
  updated_at_ms INTEGER NOT NULL
) STRICT;

CREATE TABLE env (
  id            INTEGER PRIMARY KEY,
  project_id    INTEGER NOT NULL REFERENCES project(id) ON DELETE CASCADE,
  name          TEXT    NOT NULL,
  base_url      TEXT    NOT NULL,
  variables     TEXT    NOT NULL DEFAULT '{}',   -- JSON（非敏感）
  secret_names  TEXT    NOT NULL DEFAULT '[]',   -- JSON 数组：变量名，值在 Keychain
  headers       TEXT    NOT NULL DEFAULT '{}',   -- JSON
  allow_self_signed INTEGER NOT NULL DEFAULT 0,  -- boolean
  created_at_ms INTEGER NOT NULL
) STRICT;
CREATE INDEX idx_env_project ON env(project_id);

CREATE TABLE db_connection (
  id            INTEGER PRIMARY KEY,
  project_id    INTEGER NOT NULL REFERENCES project(id) ON DELETE CASCADE,
  name          TEXT    NOT NULL,
  dialect       TEXT    NOT NULL,          -- mysql | postgres | sqlite
  dsn_encrypted BLOB    NOT NULL,          -- 加密存储（见 08）
  read_only     INTEGER NOT NULL DEFAULT 1 -- 强制只读（见 08）
) STRICT;
CREATE INDEX idx_dbconn_project ON db_connection(project_id);
```

**`ON DELETE CASCADE` 与 P5 的一致性**：删除项目时其下一切自动清理。但**删除前必须自动完整备份**（前稿 §3.2 第 6 条），且删除需要二次确认——事件日志是不可再生资产。

### 2.2 源码索引与 API 候选

```sql
CREATE TABLE source_index (
  id            INTEGER PRIMARY KEY,
  project_id    INTEGER NOT NULL REFERENCES project(id) ON DELETE CASCADE,
  git_ref       TEXT,
  file_count    INTEGER NOT NULL,
  frameworks    TEXT    NOT NULL DEFAULT '[]',  -- JSON: ["express","nestjs"]
  indexed_at_ms INTEGER NOT NULL
) STRICT;

CREATE TABLE route_candidate (
  id            INTEGER PRIMARY KEY,
  project_id    INTEGER NOT NULL REFERENCES project(id) ON DELETE CASCADE,
  source_index_id INTEGER NOT NULL REFERENCES source_index(id) ON DELETE CASCADE,
  method        TEXT    NOT NULL,
  path          TEXT    NOT NULL,
  handler_file  TEXT    NOT NULL,
  handler_line  INTEGER NOT NULL,
  framework     TEXT    NOT NULL,
  confidence    TEXT    NOT NULL,          -- high | medium
  status        TEXT    NOT NULL,          -- proposed | adopted | rejected
  doc_drift     INTEGER NOT NULL DEFAULT 0,-- 与 OpenAPI 对账：有文档但漂移
  doc_missing   INTEGER NOT NULL DEFAULT 0,-- 源码有但文档无
  proposed_by   TEXT, reviewed_by TEXT,
  reviewed_at_ms INTEGER,
  diff          TEXT                       -- JSON：人工修改记录
) STRICT;
CREATE INDEX idx_route_project_status ON route_candidate(project_id, status);
-- medium 置信度进入待复核队列（P3）：按 status 过滤计数
```

**`doc_drift` / `doc_missing` 两个布尔位**是前稿 S2 的"高测试价值点"标记的落地（[03 §1](03-测试流程.md#1-流程全景) 提到 S2 提供这些标记）。它们让"文档说了源码没说"和"源码有文档没有"成为可筛选的维度——这两类正是最值得测的地方。

### 2.3 原则库

```sql
CREATE TABLE principle (
  id            INTEGER PRIMARY KEY,
  project_id    INTEGER NOT NULL REFERENCES project(id) ON DELETE CASCADE,
  subject       TEXT    NOT NULL,          -- 如 "order.amount"
  rule          TEXT    NOT NULL,          -- 如 "≤ 50000"
  value_json    TEXT,                      -- JSON：可机读的值/范围，供参数化使用
  source_file   TEXT    NOT NULL,          -- ★ 溯源：必须可跳转
  source_line   INTEGER NOT NULL,
  layer         TEXT    NOT NULL,          -- validation | persistence | sample | comment
  confidence    TEXT    NOT NULL,          -- high | medium
  status        TEXT    NOT NULL,          -- proposed | adopted | rejected
  conflict_json TEXT,                      -- JSON：原则 vs 样本的矛盾记录
  proposed_by   TEXT, reviewed_by TEXT,
  reviewed_at_ms INTEGER,
  diff          TEXT
) STRICT;
CREATE INDEX idx_principle_project ON principle(project_id, status);
CREATE INDEX idx_principle_subject ON principle(project_id, subject);
```

`source_file` + `source_line` **非空**是刻意的：原则没有溯源就无法被验证，也无法在 diff 复核里展示"这条规则来自哪里"。([03 §2.5](03-测试流程.md#25-溯源每个用例必须能回答凭什么是这样))

`value_json` 让原则能被**参数化直接消费**（`amount ≤ 50000` → 生成 `49999/50000/50001`）。这是 S3 → S5 的关键接口，不能只存人类可读的字符串。

### 2.4 用例与运行

```sql
CREATE TABLE test_case (
  id            INTEGER PRIMARY KEY,
  project_id    INTEGER NOT NULL REFERENCES project(id) ON DELETE CASCADE,
  route_id      INTEGER REFERENCES route_candidate(id) ON DELETE SET NULL,
  name          TEXT    NOT NULL,
  description   TEXT,
  status        TEXT    NOT NULL,          -- proposed | adopted | rejected
  param_kind    TEXT    NOT NULL,          -- single | boundary | pair | matrix | sequence
  steps_json    TEXT    NOT NULL,          -- JSON：步骤树
  params_json   TEXT    NOT NULL,          -- JSON：参数集
  provenance_json TEXT  NOT NULL DEFAULT '{}',  -- JSON：溯源
  policy_json   TEXT,                      -- JSON：判定策略覆盖
  tags          TEXT    NOT NULL DEFAULT '[]',  -- JSON
  proposed_by   TEXT, reviewed_by TEXT,
  reviewed_at_ms INTEGER,
  diff          TEXT,
  created_at_ms INTEGER NOT NULL
) STRICT;
CREATE INDEX idx_case_project_status ON test_case(project_id, status);

CREATE TABLE run (
  id            INTEGER PRIMARY KEY,
  project_id    INTEGER NOT NULL REFERENCES project(id) ON DELETE CASCADE,
  env_id        INTEGER NOT NULL REFERENCES env(id) ON DELETE RESTRICT,
  plan_json     TEXT    NOT NULL,          -- ★ plan 全量快照（支持续跑与重放）
  policy_json   TEXT    NOT NULL,          -- ★ 策略快照（04 §2.3）
  seed          INTEGER NOT NULL,          -- ★ 随机种子（可复现）
  status        TEXT    NOT NULL,          -- planning|running|completed|cancelled|errored
  triggered_by  TEXT    NOT NULL,          -- human | agent | schedule | retry
  started_at_ms INTEGER NOT NULL,
  finished_at_ms INTEGER,
  event_count   INTEGER NOT NULL DEFAULT 0,
  chain_hash    TEXT,                      -- ★ 完整性校验（04 §2.4）
  counters_json TEXT                       -- 缓存投影，可重算（04 §4.3）
) STRICT;
CREATE INDEX idx_run_project_started ON run(project_id, started_at_ms DESC);
```

**`env_id` 用 `ON DELETE RESTRICT`**：不允许删除仍被历史运行引用的环境——否则历史结果的语境就丢了（"这次跑在哪个环境上"变成未知）。要删环境先归档相关运行。

**`plan_json` / `policy_json` / `seed` 三个字段是可复现性的全部依据**：有了它们，任何一次运行都能被精确重放（包括参数化生成的每一行数据）。

### 2.5 事件表（真源）

```sql
CREATE TABLE run_event (
  run_id        INTEGER NOT NULL REFERENCES run(id) ON DELETE CASCADE,
  seq           INTEGER NOT NULL,
  at_ms         INTEGER NOT NULL,
  kind          TEXT    NOT NULL,
  entry_id      TEXT,
  case_id       INTEGER,
  payload       TEXT    NOT NULL,          -- JSON；大载荷只存引用
  PRIMARY KEY (run_id, seq)
) STRICT;
-- 不建 at_ms 索引：查询永远按 (run_id, seq)，时间只是展示
```

**三个刻意的设计**：

1. **主键 `(run_id, seq)`** —— 保证同一运行内序号唯一且天然有序，判定与重放都按这个顺序。
2. **payload 是 TEXT/JSON 而非多列** —— 事件种类多（[03 §6.1](03-测试流程.md#61-事件类型) 有 11 种），每种的载荷不同。用 JSON 避免稀疏列，代价是判定时要解析。**判定在 L3/L4 层（有 JSON 能力）执行，不在 core**（[02 §2.1](02-架构.md#1-三层结构两个进程)），所以这个代价可接受。
3. **不建 `at_ms` 索引** —— 所有查询都是"某个运行内按 seq 顺序"，时间范围查询走 `run` 表的时间索引。少一个索引 = 少一份写入开销（事件表是写入最频繁的表）。

**写入路径的批处理**（[03 §6.3](03-测试流程.md#63-事件与投影的写入路径)）：攒批 32 条 + 投影行，在**一个事务**内提交。自管 SQLite 下没有语句数上限，但攒批仍有价值——它把 N 次 fsync 合并为一次，是写入吞吐的关键。

### 2.6 结果投影表

```sql
CREATE TABLE case_result (
  run_id        INTEGER NOT NULL REFERENCES run(id) ON DELETE CASCADE,
  entry_id      TEXT    NOT NULL,          -- ★ 参数化后一个 case 有多个 entry
  case_id       INTEGER NOT NULL REFERENCES test_case(id) ON DELETE CASCADE,
  param_row_label TEXT  NOT NULL,          -- 如 "金额=50001(超限)"
  intent        TEXT,                      -- baseline|boundary_low|... (03 §2.3)
  verdict       TEXT    NOT NULL,          -- passed|degraded|failed|errored|flaky|skipped
  flaky         INTEGER NOT NULL DEFAULT 0,
  duration_ms   INTEGER NOT NULL,          -- ★ 单调时钟差，非墙钟（03 §4.2）
  attempts      INTEGER NOT NULL DEFAULT 1,
  failed_asserts INTEGER NOT NULL DEFAULT 0,
  seq           INTEGER NOT NULL,          -- 该 entry 在运行中的起始序号（排序用）
  PRIMARY KEY (run_id, entry_id)
) STRICT;
CREATE INDEX idx_result_run_seq ON case_result(run_id, seq);
CREATE INDEX idx_result_case ON case_result(case_id, run_id);

CREATE TABLE step_result (
  run_id        INTEGER NOT NULL,
  entry_id      TEXT    NOT NULL,
  step_seq      INTEGER NOT NULL,
  kind          TEXT    NOT NULL,
  status        TEXT    NOT NULL,          -- ok | failed | errored | skipped
  duration_ms   INTEGER NOT NULL,
  request_ref   TEXT,                      -- artifact 引用（sha256）
  response_ref  TEXT,
  PRIMARY KEY (run_id, entry_id, step_seq)
) STRICT;

CREATE TABLE assert_result (
  run_id        INTEGER NOT NULL,
  entry_id      TEXT    NOT NULL,
  assert_seq    INTEGER NOT NULL,
  severity      TEXT    NOT NULL,          -- blocker|critical|major|minor|info
  expected      TEXT    NOT NULL,          -- ★ 快照语义（04 §2.2）：不从用例表现查
  actual        TEXT    NOT NULL,
  passed        INTEGER NOT NULL,
  principle_id  INTEGER,                   -- ★ 用于原则触发率统计（03 §7.4）
  source_file   TEXT, source_line INTEGER, -- 断言依据的源码位置
  PRIMARY KEY (run_id, entry_id, assert_seq)
) STRICT;
CREATE INDEX idx_assert_principle ON assert_result(principle_id);
```

**`case_result` 主键是 `(run_id, entry_id)` 而非 `(run_id, case_id)`** —— 这是参数化的直接结果（[03 §2.3](03-测试流程.md#23-参数化一组用例-一次运行的多条记录)）。同一个 case 在一次运行里有 N 个 entry，每个 entry 是独立的执行单元和独立的判定。**这是本稿相对前稿最重要的 schema 差异**：前稿的用例模型没有参数化维度，表结构也就无法表达"3 个边界值中 1 个失败"。

**`assert_result` 里冗余存 `expected` / `actual`** —— 刻意的快照语义（[04 §2.2](04-结果模型.md#22-事件必须自足)）。用例被人工修改后，历史运行的断言期望**不变**。

**`principle_id` 为空的断言是合法且有用的** —— 表示"这个断言没有原则依据"（如状态码断言）。统计原则触发率时只看非空值。

### 2.7 Artifact 表

```sql
CREATE TABLE artifact (
  sha256        TEXT    PRIMARY KEY,
  size_bytes    INTEGER NOT NULL,
  content_type  TEXT,
  storage       TEXT    NOT NULL,          -- inline | file
  inline_data   BLOB,                      -- 小于阈值（默认 64 KiB）直接内联
  file_path     TEXT,                      -- 超阈值落文件
  truncated     INTEGER NOT NULL DEFAULT 0,-- 是否被截断
  original_size INTEGER,                   -- 截断前的真实大小
  created_at_ms INTEGER NOT NULL,
  retain_until_ms INTEGER                 -- ★ 保留策略（04 §7.1）
) STRICT;
CREATE INDEX idx_artifact_retain ON artifact(retain_until_ms);
```

**`sha256` 作主键实现天然去重**：同一份响应体在多次运行中被引用时只存一份。API 测试里重复响应很常见（相同请求相同返回），去重能显著节省空间。

**`truncated` + `original_size` 必须同时记录**：界面上要显示"完整报文 2.4 MB，已截断显示前 64 KB"（[05 §4.3](05-结果呈现.md#43-详情面板从数字追问到证据)）。只标记截断而不说原文多大，用户无法判断是否值得去找完整报文。

**`inline` vs `file` 的分界**：内联进 SQLite 的是小对象（默认 ≤ 64 KiB）。阈值不宜过大的实际理由是**读放大**——详情面板一次查询若把多个大 BLOB 拉进内存会拖慢界面。超过阈值的落文件，库里只留路径。

### 2.8 Agent 会话表

```sql
CREATE TABLE agent_session (
  id            INTEGER PRIMARY KEY,
  project_id    INTEGER NOT NULL REFERENCES project(id) ON DELETE CASCADE,
  kind          TEXT    NOT NULL,          -- api_discovery | principle_extract | case_synth
  checkpoint    BLOB,                      -- libfx checkpoint（由边车回传落库）
  turn_count    INTEGER NOT NULL DEFAULT 0,
  created_at_ms INTEGER NOT NULL,
  updated_at_ms INTEGER NOT NULL
) STRICT;

CREATE TABLE agent_turn (
  session_id    INTEGER NOT NULL REFERENCES agent_session(id) ON DELETE CASCADE,
  turn_seq      INTEGER NOT NULL,
  role          TEXT    NOT NULL,
  content       TEXT    NOT NULL,          -- 脱敏后（08）
  tool_name     TEXT,
  tokens_in     INTEGER, tokens_out INTEGER,
  at_ms         INTEGER NOT NULL,
  PRIMARY KEY (session_id, turn_seq)
) STRICT;
```

**`checkpoint` 是 BLOB 且可能为空**：libfx 的 checkpoint 由宿主持久化（[01 §3.1](01-定位与原则.md#31-libfx-真实且贵方已在用仍然采用)）。宿主是 worker 线程，因此**直接 `db.saveCheckpoint()` 即可**——前一版因宿主是边车而需要一整套 base64 + IPC 回传协议，现已消除（[07](07-Agent与人机门.md)）。

**`agent_turn` 与 `run_event` 分开的理由**：前者是"AI 说了什么"，后者是"测试发生了什么"。它们的生命周期、保留策略、查询模式都不同。混一张表会让两边的查询都变慢。

## 3. 命名查询清单

`src/queries.sql` 的关键查询。`:live` 标记的会在被依赖表写入后自动重跑。

```sql
-- name: runHeader :live
SELECT r.id, r.status, r.started_at_ms, r.finished_at_ms,
       r.event_count, r.counters_json, e.name AS env_name
FROM run r JOIN env e ON e.id = r.env_id
WHERE r.id = :run_id;

-- name: runCaseRows :live          ← ★ 结果表的实时数据源（05 §3.2）
SELECT cr.entry_id, cr.case_id, c.name, c.status AS case_status,
       rc.method, rc.path AS route_path,
       cr.param_row_label, cr.intent, cr.verdict, cr.flaky,
       cr.duration_ms, cr.attempts, cr.failed_asserts, cr.seq
FROM case_result cr
JOIN test_case c ON c.id = cr.case_id
LEFT JOIN route_candidate rc ON rc.id = c.route_id
WHERE cr.run_id = :run_id
ORDER BY cr.seq
LIMIT :limit OFFSET :offset;

-- name: runProgress :live          ← ★ 进度条（派生，不存字段）
SELECT COUNT(*) AS done_entries,
       SUM(CASE WHEN verdict IN ('passed','degraded','flaky') THEN 1 ELSE 0 END) AS ok,
       SUM(CASE WHEN verdict = 'failed'   THEN 1 ELSE 0 END) AS failed,
       SUM(CASE WHEN verdict = 'errored'  THEN 1 ELSE 0 END) AS errored,
       SUM(CASE WHEN verdict = 'degraded' THEN 1 ELSE 0 END) AS degraded,
       SUM(CASE WHEN flaky = 1            THEN 1 ELSE 0 END) AS flaky
FROM case_result WHERE run_id = :run_id;

-- name: entryDetail :live
SELECT sr.step_seq, sr.kind, sr.status, sr.duration_ms,
       sr.request_ref, sr.response_ref
FROM step_result sr
WHERE sr.run_id = :run_id AND sr.entry_id = :entry_id
ORDER BY sr.step_seq;

-- name: entryAsserts :live
SELECT ar.assert_seq, ar.severity, ar.expected, ar.actual, ar.passed,
       ar.principle_id, ar.source_file, ar.source_line
FROM assert_result ar
WHERE ar.run_id = :run_id AND ar.entry_id = :entry_id
ORDER BY ar.assert_seq;

-- name: insertRunEvent :exec
INSERT INTO run_event (run_id, seq, at_ms, kind, entry_id, case_id, payload)
VALUES (:run_id, :seq, :at_ms, :kind, :entry_id, :case_id, :payload);

-- name: upsertCaseResult :exec
INSERT INTO case_result (run_id, entry_id, case_id, param_row_label, intent,
                         verdict, flaky, duration_ms, attempts, failed_asserts, seq)
VALUES (:run_id, :entry_id, :case_id, :param_row_label, :intent,
        :verdict, :flaky, :duration_ms, :attempts, :failed_asserts, :seq)
ON CONFLICT(run_id, entry_id) DO UPDATE SET
  verdict = excluded.verdict, flaky = excluded.flaky,
  duration_ms = excluded.duration_ms, attempts = excluded.attempts,
  failed_asserts = excluded.failed_asserts;

-- name: recentRuns
SELECT id, status, started_at_ms, finished_at_ms, counters_json,
       started_at_ms AS label_ms
FROM run WHERE project_id = :project_id
ORDER BY started_at_ms DESC LIMIT :limit;

-- name: flakyCases                ← ★ 跨运行聚合（04 §3.4），查询期算
SELECT c.id, c.name, rc.method, rc.path,
       COUNT(*) AS runs,
       SUM(CASE WHEN cr.flaky = 1 THEN 1 ELSE 0 END) AS flaky_runs
FROM case_result cr
JOIN test_case c ON c.id = cr.case_id
LEFT JOIN route_candidate rc ON rc.id = c.route_id
WHERE cr.run_id IN (SELECT id FROM run WHERE project_id = :project_id
                    ORDER BY started_at_ms DESC LIMIT :window)
GROUP BY c.id
HAVING flaky_runs > 0
ORDER BY flaky_runs DESC LIMIT :limit;

-- name: uncoveredRoutes            ← ★ 覆盖视图（05 §7.2），LEFT JOIN 求差集
SELECT rc.id, rc.method, rc.path, rc.confidence
FROM route_candidate rc
LEFT JOIN test_case c ON c.route_id = rc.id
WHERE rc.project_id = :project_id
  AND (rc.status = 'adopted' OR rc.confidence = 'high')
  AND c.id IS NULL
ORDER BY rc.path;

-- name: principleEffectiveness      ← ★ 原则触发率与零检出（03 §7.4）
SELECT p.id, p.subject, p.rule, p.source_file, p.source_line,
       COUNT(DISTINCT c.id)                     AS cases_referencing,
       SUM(CASE WHEN ar.passed = 0 THEN 1 ELSE 0 END) AS violations_detected
FROM principle p
LEFT JOIN test_case c ON c.project_id = p.project_id AND c.provenance_json LIKE '%' || p.id || '%'
LEFT JOIN assert_result ar ON ar.principle_id = p.id
WHERE p.project_id = :project_id AND p.status = 'adopted'
GROUP BY p.id ORDER BY violations_detected DESC;
```

**两处 SQL 需要说明**：

1. **`principleEffectiveness` 里的 `c.provenance_json LIKE`** 是 JSON 字段上的粗匹配——因为溯源存成 JSON 数组而非关联表。**这是一个有意的取舍**：溯源是"记录"而非"查询维度"，为它建关联表（`case_principle_ref`）会让用例写入路径复杂化，而这条统计查询的频率很低（打开统计视图时才算一次）。如果将来需要高效查询，再加迁移。

2. **`flakyCases` 的子查询里 `IN (SELECT ... LIMIT)`** —— SQLite 支持，但要注意 `LIMIT` 子查询在窗口语义上等价于"最近 N 次运行"，这正是需求。

**查询与推流的权衡**：结果表、进度、运行头、详情面板这些**运行中会变**的视图订阅 IPC 推送（[02 §5](02-架构.md#43-实时推送由页面轮询驱动)）；统计类查询（flaky / 覆盖 / 原则效率）在打开视图时查一次即可。**不要把一切都做成实时的**——统计查询不需要实时，订阅只会浪费。

## 4. 投影与事件的一致性

### 4.1 投影必须可从事件重建

**验证方式**（应当作为一条集成测试）：

```
① 取一个已完成的 run
② 备份其 case_result / step_result / assert_result 行
③ 删除这些投影行
④ 从 run_event 全量重算并重建投影
⑤ 比对：必须逐字段一致
```

这条测试一旦通过，就证明了 P1 的"投影可重建"不是口号。**它必须在 M1 就建立**——等到有几百个运行、schema 改过几轮之后再补，就再也补不上了。

### 4.2 事件与投影写入的原子性

[03 §6.3](03-测试流程.md#63-事件与投影的写入路径) 已定：**同一批的事件与投影行必须在同一个事务里提交**。

```sql
-- 一次事务的内容
INSERT INTO run_event ...;   -- 事件 1..N
INSERT INTO run_event ...;
INSERT INTO case_result ...; -- 投影（upsert）
INSERT INTO step_result ...;
INSERT INTO assert_result ...;
```

原因：如果事件提交了但投影没提交，界面会通过 `:live` 查到一个"事件说完成了，但结果表没这一行"的不一致状态。原子性能杜绝这类瞬时错乱。

**注意 64 语句上限**：一批 32 条事件 + 若干投影行要控制在 64 内。如果某个 entry 的断言特别多（比如 20 条断言），需要**拆成多个事务**——但拆分会短暂产生"事件有、投影不全"的窗口。**缓解**：让事件先于投影成批提交（事件批 N，投影批 N），并在 UI 上容忍"末批投影未到"（因为 `:live` 会在下一批提交后自动修正）。

### 4.3 事件表的增长与维护

预估规模：556 个 entry 的运行约 1,284 条事件（[05 §2.1](05-结果呈现.md#21-整体骨架) 的示例数字）。每天 5 次运行 → 约 6,400 条/天 → 每年 230 万条。

**这个规模对 SQLite 完全无压力**，但需要两个维护动作：

| 动作 | 时机 | 说明 |
|---|---|---|
| `PRAGMA incremental_vacuum` | 定期 / artifact 清理后 | 回收空间。**自管 SQLite 下可直接执行**（前一版因引擎限制不能在运行期执行） |
| 索引重建 | 不需要 | 事件表只有主键索引；结果表索引变化很小 |

**自管 SQLite 下**，VACUUM / `incremental_vacuum` 可在运行时执行（建议在空闲时或应用启动时做，避免阻塞）。这也简化了 M6 的便携包导出——可在导出前整理数据库。

## 5. 与 UI 层的数据契约

回到 [02 §3](02-架构.md#3-代码结构)：主进程通过仓储函数读写数据，类型由 TypeScript 定义（无代码生成）。

```ts
// 类型定义（手写，与 SQL 一一对应）
interface RunCaseRowsRow {
  readonly entry_id: Uint8Array;        // TEXT → Uint8Array（NS1024）
  readonly case_id: number;
  readonly name: Uint8Array;
  readonly route_path: Uint8Array | null;
  readonly param_row_label: Uint8Array; // ★ 参数行标签（参数化实体）
  readonly verdict: Uint8Array;         // 文本标签；比较用内容相等（===）
  readonly flaky: number;               // 0/1
  readonly duration_ms: number;
  readonly attempts: number;
  readonly failed_asserts: number;
  readonly seq: number;
}
```

**TEXT 列一律映射为 `Uint8Array`**（官方：TEXT/BLOB rows are `Uint8Array`）——这正好与 NS1024（禁 string 字段）一致，不需要额外处理。

**verdict 用文本而非整数**：可读性（直接看库能懂）、演进友好（加新 verdict 不用改枚举映射）。文本比较在子集里是**内容相等**（官方："`===` on `string`-typed values — content equality"），可以直接 `if (row.verdict === verdictPassed)` 判断，无需解码。

**但注意**：`row.verdict` 是 `Uint8Array`，不能直接与字符串字面量比较。需要预先用 `asciiBytes("passed")` 构造常量（[01 §3.4](02-架构.md#3-代码结构) 提到的 `asciiBytes` 在编译期变 rodata，零成本）：

```ts
import { asciiBytes } from "@native-sdk/core";
const V_PASSED: Uint8Array = asciiBytes("passed");
const V_DEGRADED: Uint8Array = asciiBytes("degraded");
// 派生函数里：
export function isOk(r: RunCaseRowsRow): boolean {
  return r.verdict === V_PASSED || r.verdict === V_DEGRADED;
}
```

**这是"文本即字节"约束下的标准写法**，应当作为项目约定写进代码规约。

## 6. 数据位置与备份

| 数据 | 位置 | 备份 |
|---|---|---|
| `app.db`（全部业务表） | 引擎拥有的 app-data 目录 | 项目导出 / 便携包（M6） |
| artifact 文件 | app-data 下的 artifacts 目录 | 随项目导出（可选，体积大） |
| 凭据（AI Key / 数据库密码） | **OS 钥匙串**（macOS `security` CLI / keytar / 自写加密） | **不备份**（设备绑定，符合安全预期） |
| 源码副本 | app-data 下的 sources/<projectId> | 可从 git 重新拉取（记录 ref） |

**凭据不进备份是刻意的**：导出的便携包可能被分享，密码不该在里面。目标是"带数据的迁移"，凭据在目标机器重新输入。

**数据库 schema 版本与迁移锁**：`migrations.lock.json` 必须随代码提交，且**应用启动时要检查**库的已应用迁移是否与代码一致——不一致就拒绝启动并提示（而不是静默用错误的 schema 跑）。测试数据的正确性依赖于 schema 的正确性。

## 7. 小结

| 约束（来自实测） | 设计应对 |
|---|---|
| STRICT 表 + 只增迁移 | schema 只加不改；破坏性变更走四步法 |
| 单次结果 ≤ 8192 行 / 8 MiB | 结果表分页 + 虚拟化；artifact 大对象落文件 |
| exec ≤ 64 语句一事务 | 攒批 32 事件 + 投影，超限拆批 |
| TEXT → `Uint8Array` | 与 NS1024 天然一致；用 `asciiBytes` 常量比较 |
| 生命周期 PRAGMA 被拒 | VACUUM 走 CLI / 迁移，不在运行期 |
| `:live` 有追踪开销 | 只给结果表/进度/详情用 live，统计查询用普通查询 |

**最重要的两个 schema 决策**：

1. **`case_result` 主键 `(run_id, entry_id)`** —— 参数化是一等维度，"3 个边界值中 1 个失败"必须能被表达。
2. **`assert_result` 冗余存 expected/actual** —— 快照语义，保证历史运行的判定不因用例被修改而追溯改变。
