# 05 · 测试流程与结果的呈现

> ★ 本次设计的重点章节之一。
> 本文把 [03 的流程](03-测试流程.md)与 [04 的结果模型](04-结果模型.md)翻译成**界面**。
> 技术选型见 [10](10-技术选型.md)，进程与 IPC 见 [02](02-架构.md)。
> **Web 栈（React + Vite）解除了前一版 Native markup 的能力限制**，呈现能力实际更强——§7 与 §8 是明显受益的部分。

---

## 1. 呈现的三条原则

### 1.1 一切呈现都是投影

界面不持有真相。渲染进程绑定的是主进程从 SQLite 查出的投影行，投影行来自事件日志（[04 §1](04-结果模型.md#1-三层分离)）。

**推论**：界面刷新不需要自建推送通道去承载数据，只需"主进程推通知、界面更新 state"（[02 §5](02-架构.md#43-实时推送由页面轮询驱动)）。

### 1.2 derive-don't-store

通过率、进度、分页切片、状态色都是**派生值，不存 state**。

```ts
// 派生函数（纯，可测试）—— 不放进 store
export const passRate = (rows: CaseRow[]): number => {
  const total = rows.length;
  if (total === 0) return 0;
  const ok = rows.filter(r => r.verdict === 'passed' || r.verdict === 'degraded').length;
  return (ok * 100) / total;
};

// 组件里直接用
const rate = useMemo(() => passRate(rows), [rows]);
```

**这消灭了"派生字段忘了更新"这一整类 bug**，且这些函数可独立单测（前一版因要在闭子集里写，测试价值被削弱）。

### 1.3 不可信输入必须转义

被测源码、数据库内容、API 响应都会进入界面（[08 §4.4](08-安全基线.md#44-ai-上下文的额外约束)）。**严禁 `dangerouslySetInnerHTML`**；代码高亮必须用支持转义的库（Shiki 输出转义后的 HTML，CodeMirror 是 DOM 渲染）；Markdown 用 `react-markdown` + `rehype-sanitize`。

**这条在前一版不构成问题**（Native markup 无 HTML 注入面），但在 Web 栈下是**必须显式规定的纪律**。

**布局实现**：CSS Grid（`grid-template-columns: 220px 1fr 330px`）；中栏与右栏之间的分隔用 `react-resizable-panels` 或自写拖拽（前一版用 Native SDK 的 `split` 组件）。

**右栏常驻而非抽屉**：人机协同是核心，Agent 面板被藏起来就等于没有。

### 2.2 顶栏：项目作用域是第一公民

```tsx
<header className="topbar">
  <ProjectSwitcher
    projects={projects}
    activeId={activeProjectId}

  <Spacer />

  <IconButton icon="command" onClick={openPalette} />
  <IconButton icon="settings" />

```

**切换项目 = 切换全部作用域**（P5）：

```ts
case 'project_switch':
  // 清空所有视图状态，重新加载当前页签数据（新 projectId）
  return { ...state, activeProjectId: action.id, rows: [], selection: null, page: 0, filter: DEFAULT };
```

**为什么切换要"清空重查"而不是"合并"**：任何残留的前一项目数据都是隔离泄漏。宁可重新加载（短暂 loading），不可显示跨项目数据。

### 2.3 视觉规范

| 元素 | 规范 | 理由 |
|---|---|---|
| 深色为主 | 深底 + 高对比文本 | 长时间盯测试结果；与 deepStudio 视觉语言一致 |
| verdict 六色 | pass 绿 / degraded 黄 / failed 红 / errored 灰 / flaky 紫 / skipped 暗灰 | **必须色盲友好**（见下） |
| 等宽字体 | 报文、路径、源码行、变量值 | 对比字符差异（`l`/`1`/`O`/`0`）是排查日常 |
| 数字右对齐 | 所有计数、耗时、百分比 | 列对齐才能扫读 |
| 时长格式 | < 1s 用 ms；≥ 1s 用 s（1 位小数） | 避免 "1203ms" 与 "1.2s" 混用 |

**色盲友好**：约 8% 男性有红绿色觉障碍，而本界面**完全依赖颜色传达核心信息**。每个 verdict 必须配**形状/图标**冗余编码：

| verdict | 颜色 | 图标 |
|---|---|---|
| passed | 绿 | `✓` |
| degraded | 黄 | `!` |
| failed | 红 | `✗` |
| errored | 灰 | `⌁` |
| flaky | 紫 | `◐` |
| skipped | 暗灰 | `–` |

配色用 CSS 变量（`--verdict-pass` 等），**对比度用 axe 在 CI 中校验**（§10）。

## 3. 实时刷新机制

### 3.1 路径

```
主进程 runner 执行一步
  → ① 写事件 + 投影（SQLite 单事务）
  → ② 攒批（32 条 / 100ms）后 webContents.send('push:runEvents', batch)
  → ③ 渲染进程 store.applyEvents(batch) 增量更新
  → ④ 虚拟表格重渲染受影响的行
```

**顺序纪律**（[02 §5.1](02-架构.md#43-实时推送由页面轮询驱动)）：**先落库、再推送**。保证推送内容一定已持久化——崩溃后重连不丢数据。

### 3.2 增量应用 + 定期对账

```ts
// store：增量应用推送
applyEvents(batch: RunEventDto[]) {
  const affected = new Map<number, Partial<CaseRow>>();
  for (const e of batch) {
    if (e.entryId != null) affected.set(e.entryId, mergeRow(affected.get(e.entryId), e));
  }
  set(s => ({ rows: s.rows.map(r => affected.has(r.entryId) ? { ...r, ...affected.get(r.entryId) } : r) }));
}

// 每 5 秒全量对账，修正累积误差
useEffect(() => {
  const t = setInterval(() => refetchRunRows(runId), 5000);
  return () => clearInterval(t);
}, [runId]);
```

**为什么需要定期对账**：增量应用可能因竞态（推送乱序、组件卸载期间漏收）累积误差。全量对账廉价且彻底。**纯增量易漂移，纯轮询延迟高——两者结合最稳。**

### 3.3 相对于前一版：限制消失

前一版因为没有流式订阅，只能绕道 SQLite `:live` 查询，并且受限：

| 前一版的限制 | 新版 |
|---|---|
| 单次查询结果 ≤ 8192 行 / 8 MiB | 无硬限制（分页仍是好实践） |
| `:live` 依赖集追踪（不确定能否覆盖多表 JOIN，曾是待验证项 V2） | **不存在此问题** |
| `Sub.timer` 是唯一订阅 | 任意定时/订阅模式 |
| Agent 流式必须复用同一通道 | 独立 channel（`push:agentDelta`） |

**保留自前一版的洞察**：实时通道与历史存储走同一条路径——能实时看到的就一定能事后回放。**推送的内容必须是已落库的内容**（§3.1 的顺序纪律就是这个洞察的落地）。

**★ 两处相对前一版的显著提升**：Monaco/CodeMirror 级报文查看（可搜索、可折叠大 JSON）与任意图表类型。

### 4.3 详情面板：从数字追问到证据

五个页签（[04 §4.3](04-结果模型.md#43-结果的可解释性从数字追问到证据)）：

**① 断言时间线**（主视图）

```
● 状态码 200 == 200                       ✓ 通过   (blocker)
│   期望 200 · 实际 200
│
✗ 响应体 error.code == "AMOUNT_EXCEEDED"   ✗ 失败   (critical)
│   期望 "AMOUNT_EXCEEDED" · 实际 500 · 第 3/3 次尝试
│   ↳ 依据 原则#12 金额上限 50,000  →  order.controller.ts:88  [跳转源码]
│
○ 响应头 X-Request-Id 存在                 ! 降级   (minor)
    期望 存在 · 实际 缺失
```

**每行显示 severity 与期望/实际**；失败断言默认展开。

**② 请求报文**：method / URL（path 与 query 分段高亮）/ headers（敏感值 `••••`，可点击临时揭示——**揭示动作写审计**）/ body（Shiki 高亮 JSON，超长折叠）。

**③ 响应报文**：同上，加 status + 耗时 + 重定向链。大响应体显示"完整报文 2.4 MB，当前显示前 64 KB [打开完整报文]"。

**④ 溯源**：

```
原则 (2)
  · 金额上限 50,000          order.controller.ts:88   [跳转源码]
  · 金额必须为正数            create-order.dto.ts:24   [跳转源码]
真实样本 (1)
  · orders.amount 分布: min=1 max=49999 p95=3200   表 orders (已脱敏)
Agent 会话
  · session-a3f2 · turn 4 · 采纳自 proposed#118
```

**跳转源码**用 `vscode://file/path:line` 协议（直接定位到行）或 `shell.openPath`。这是 deepStudio「点击节点定位 MBT 行」的对应手法。

**⑤ 重试历史**：每次尝试的原因、耗时、结果。"前两次 connect_failed，第三次断言失败"——这正是 `flaky` 标记的依据。

### 4.4 新失败的强调

diff 结果（[04 §5.3](04-结果模型.md#53-重判与对账diff是同一机制)）必须有强提示：

- **运行头之上**：Alert 条 `⚠ 相比 #127 新增 3 个失败`（可点击跳到"仅已变更"筛选）
- **结果表**：新失败的行走橙色左边框 + `NEW` 角标
- **默认排序**：`newFailures` 优先

**理由**：92% 通过率本身不构成行动信号；"比上次多了 3 个失败且都在订单接口"才构成。

### 4.5 空状态与进行中状态

| 状态 | 内容 |
|---|---|
| **R1 无项目** | 产品定位 + 三个接入入口（Git / 本地 / zip）+ 流程说明 |
| **R2 有项目未发现 API** | 引导跑 S2；"尚未索引源码 [开始索引]" |
| **R3 有 API 无用例** | 引导合成；"32 个接口尚未覆盖 [生成用例]" |
| **R4 运行中** | 结果表实时增长 + 进度推进（**这是"进行中"而非"空"**） |
| **R5 全通过** | 不要只有绿勾。显示 note 输入框（"可添加备注记录本次上下文"）+ 覆盖率提示 |

**运行中的额外处理**：状态栏显示当前 in-flight 用例名 + 参数行标签。若某 entry 耗时超过该 kind 的 p95 两倍，该行显示"耗时异常"角标——**实时诊断价值**。

**"未覆盖"分组是必备的**：把"哪些接口还没测"变成一等可见信息（[04 §4.1](04-结果模型.md#41-投影清单)）。测试工作台最大的风险不是失败多，而是**覆盖率看起来高但有大片空白**。

**溯源芯片三级视觉**（[03 §2.5](03-测试流程.md#25-溯源每个用例必须能回答凭什么是这样)）：`🔗 file:line`（有原则溯源，绿边）/ `📊 table (样本)` / `⚠ 无原则溯源`（黄边警示）。

### 5.2 用例详情：步骤树 + Diff 复核

```
▼ 用例: 金额边界值验证                       [已采纳] · 溯源 2 条
  ▼ 参数集: boundary (3 行)                   [编辑参数]
    • 金额=49999 (边界内)        intent: boundary_low
    • 金额=50000 (边界)          intent: boundary_high   [NEW]
    • 金额=50001 (超限)          intent: invalid
  ▼ 步骤 (4)
    1. request  POST {{env.baseUrl}}/orders/create
                 body: { amount: {{var.amount}}, ... }
    2. assert   状态码 == 200                    [blocker]
    3. assert   响应体 error.code == "AMOUNT_EXCEEDED"  [critical]
                 ↳ 溯源: order.controller.ts:88
    4. db_check orders WHERE amount = {{var.amount}}
                 ↳ 超限时应无新行
```

**Diff 复核视图**（人工修改 AI 草稿时的双栏对照）：

```
┌─ Agent 草稿 ──────────────┬─ 人工修改 ────────────────┐
│ 3. assert                 │ 3. assert                 │
│    响应体 msg == "金额超限"│    响应体 error.code ==    │
│    severity: major        │      "AMOUNT_EXCEEDED"    │
│                           │    severity: critical  ▲  │
└───────────────────────────┴───────────────────────────┘
  ▲ 差异 2 处   [采纳人工版本] [保留草稿] [重新生成]
```

用**行级 diff 库**（`diff` npm 包）计算差异并高亮，比手写对照更准确。

## 7. 趋势与统计视图

### 7.1 能力（相对前一版的提升）

前一版受限于 Native SDK 的 `chart` 只有 line / bar / band。**Web 栈下没有这个限制**：

| 想表达 | 前一版 | 新版 |
|---|---|---|
| 通过率随时间 | line | line / area（uPlot） |
| 各 verdict 构成 | band 或手拼 bar | **堆叠面积 / 堆叠柱 / 环形** |
| 耗时分布 | 无直方图，需手工分桶 | **直方图 / 箱线图 / 散点** |
| 慢用例排序 | 手拼 bar | 横向 bar 或表格 + 条形 |
| 用例 × 运行矩阵 | 色块网格 | 色块网格（visx heatmap 或自写） |
| p95 / p99 趋势 | 需多次查询 | 一次查询 + 多序列折线 |

**建议**：趋势类用 **uPlot**（极小极快，适合时间序列），分布与构成类用 **recharts**（类型全、API 友好），按需引入。

## 8. Copilot 侧栏（协同界面）

Agent 细节见 [07](07-Agent与人机门.md)，此处定呈现形态。

```
┌─ Copilot ─────────────────────────────────┐
│ 会话 session-a3f2          [检查点 ✓] [×] │
│ ───────────────────────────────────────── │
│ 🤖 正在分析 POST /orders/create ...        │
│    ▸ 读取源码 create-order.dto.ts          │
│    ▸ 关联原则 2 条                          │
│    ▸ 采样 orders.amount                    │
│    ✓ 生成 3 个用例草稿（待复核）             │
│                                            │
│ ┌─ 建议卡（有溯源）─────────────────────┐  │
│ │ 金额边界值验证                        │  │
│ │ 🔗 依据: order.controller.ts:88       │  │
│ │ [采纳] [编辑] [拒绝]                  │  │
│ └──────────────────────────────────────┘  │
│ ┌─ 建议卡（无溯源）─────────────────────┐  │
│ │ ⚠ 订单幂等性验证                      │  │
│ │ ⚠ 无原则溯源，仅基于 Agent 推断        │  │
│ │ [采纳] [编辑] [拒绝]                  │  │
│ └──────────────────────────────────────┘  │
│                                            │
│ ───────────────────────────────────────── │
│ [输入指令…                        ] [发送] │
└────────────────────────────────────────────┘
```

**流式输出**：libfx 的 `for await (event of turn)` 在主进程，`text_delta` 经攒批后 `push:agentDelta` 推送（[02 §5.2](02-架构.md#43-实时推送由页面轮询驱动)）。

**★ 相对前一版的提升**：libfx 在主进程直接可用，**不需要边车 IPC 转发**。前一版为此设计了完整的边车协议 + checkpoint base64 回传——现在是一次函数调用加 `db.saveCheckpoint()`。

**步骤时间线**（`▸ 读取源码`）来自 libfx 的 `tool_start` 事件，让用户看到 Agent **正在做什么**。

**建议卡两种视觉**（[03 §2.5](03-测试流程.md#25-溯源每个用例必须能回答凭什么是这样)）：有溯源（正常边框 + `🔗 依据`）/ **无溯源（黄边 + 显式警示）**——这是 P3「AI 不越权」的视觉体现，让用户在采纳前就知道有没有依据。

**Markdown 渲染**：Agent 输出可能含 Markdown。用**安全转义**的渲染器（`react-markdown` + `rehype-sanitize`）——**这是不可信输入**（[§1.3](#13-不可信输入必须转义)）。

## 10. 无障碍与键盘

**Web 栈在这方面的能力远强于前一版**（有成熟工具链与标准）：

| 项 | 要求 | 验证 |
|---|---|---|
| 颜色不单独承载信息 | 每个 verdict 配图标（§2.3） | 人工评审 |
| 对比度 | 深色主题文本 ≥ 4.5:1；verdict 色块上的文本单独校验 | **axe 在 CI 自动检查** |
| 语义化 HTML | 结果表用 `<table>` 语义（不是 div 拼） | axe |
| ARIA | Tabs/Dialog/Tooltip 用 Radix（自带正确 ARIA） | axe |
| 键盘可达 | 结果表 ↑↓ 移动、Enter 展开、Esc 收起 | Playwright 键盘测试 |
| 焦点可见 | 明确的 focus ring（不 `outline: none`） | 人工评审 |
| 快捷键 | `⌘K` 命令面板、`⌘R` 运行、`⌘.` 停止、`⌘⇧D` 对比、`⌘F` 搜索、`⌘1..6` 切页签 | 帮助菜单可查 |

**`axe` 进 CI 是可执行的硬约束**——前一版靠 Native SDK 的 `native check`，新版用 `@axe-core/playwright` 达到同等效果且更成熟。

**结果表的键盘导航尤其重要**：排查失败时会连续 ↑↓ 扫行、Enter 展开，必须用鼠标会慢一个量级。

## 11. 性能

渲染进程（系统 WebView）的性能要点：

| 场景 | 措施 |
|---|---|
| 万行结果表 | `@tanstack/react-virtual` 只渲染可视行 |
| 高频事件推送 | 主进程攒批 32/100ms；渲染进程增量应用（§3.2） |
| 大 JSON 报文 | 折叠 + 虚拟化；**不要一次性渲染 10 万行 JSON** |
| 派生计算（通过率等） | `useMemo` 缓存，依赖 `rows` 变化才重算 |
| 图表 | uPlot 用 canvas（比 SVG 快得多）；数据点 > 2k 时降采样 |
| 长列表搜索 | 防抖 200ms + **在主进程做**（SQL `LIKE` 比前端过滤快） |
| 内存 | 大 artifact 不驻留渲染进程，按需从主进程拉取 |

**一条纪律**：**重计算在主进程或 worker，渲染进程只做展示**。这是 [02 §6](02-架构.md#5-worker-池的组织) 分工的延伸。

## 12. 与前版的差异小结

| 维度 | 前一版（Native markup） | 新版（React） |
|---|---|---|
| 实时通道 | SQLite `:live` 查询（绕路，有 8 MiB 限制） | **IPC 推送 + 增量对账**（无限制） |
| 结果表 | `virtual list` 组件 | **`@tanstack/react-virtual`**（更灵活：自定义行样式/分组/固定列） |
| 断言时间线 | `timeline` 组件 | 自写（语义化 `ol`，完全可控） |
| 报文查看 | 只读 `code` 组件 | **Shiki / CodeMirror**（可搜索、可折叠、可跳转） |
| 图表 | 仅 line / bar / band | **任意图表**（uPlot + recharts） |
| 文本处理 | 禁 `string` 字段，文本即字节 | **无限制** |
| Agent 流式 | 边车 IPC 转发 + 复用 `:live` | **主进程直接推送** |
| 无障碍 | Native SDK 的机器校验 | **axe + Playwright**（更成熟） |
| 组件库 | 仅内置组件目录 | **Radix + 任意 npm 生态** |
| 样式 | design tokens | **Tailwind + CSS 变量** |

**保留自前一版的呈现设计**（与栈无关）：

- 六态 verdict 的颜色 + 图标双重编码
- "未覆盖"分组的可见性
- 溯源芯片的三级信任度视觉
- 新失败置顶 + `NEW` 角标
- 只读视图"不出现而非禁用"的纪律
- 五种空状态（含"运行中"与"全通过"）
- 状态栏显示并发度
- 从数字三步追问到证据
