# 04 · 结果模型

> ★ 本次设计的重点章节之一。
> 本文回答三个问题：**结果的事实是什么**、**结论怎么算出来**、**为什么这个结论将来还能被推翻重算**。
> 核心判断：结果的真源是**追加式执行事件日志**，不是结果表；判定是**纯函数**，因此可以演进并对历史运行重算。
> 呈现层如何消费这些结论，见 [05](05-结果呈现.md)；存储落地见 [06](06-数据模型.md)。

---

## 1. 三层分离

测试结果最容易被做成一团：执行代码里顺手写判定，判定结果顺手写进表，表又被当作事实去算统计。一旦这样，就再也无法回答"上周那次失败，用今天的规则看还算失败吗"。

本稿强制三层分离：

```
┌──────────────────────────────────────────────────────────────┐
│ 第 1 层 · 事实（Fact）                                        │
│ 追加式事件日志 run_event：只记录"观测到了什么"                  │
│ 不可变、只追加、带单调 seq                                     │
│ 例：status=500、durationMs=1203、body 的 sha256               │
└────────────────────────┬─────────────────────────────────────┘
                         │ 投影（纯函数，可重跑）
                         ▼
┌──────────────────────────────────────────────────────────────┐
│ 第 2 层 · 判定（Verdict）                                     │
│ verdict = reduce(events, policy)                             │
│ 纯函数：不读时钟、不读网络、不读随机                             │
│ 例：passed / failed / degraded / errored / flaky / skipped    │
└────────────────────────┬─────────────────────────────────────┘
                         │ 投影（视图期派生）
                         ▼
┌──────────────────────────────────────────────────────────────┐
│ 第 3 层 · 展示（Projection）                                  │
│ 通过率 / 趋势 / 慢用例榜 / 不稳定榜 / 报告导出                   │
│ 全部在查询期或视图期计算，不落聚合表                             │
└──────────────────────────────────────────────────────────────┘
```

**关键性质**：第 1 层永不修改，第 2 层可以随时用新规则重算，第 3 层永远从第 2 层算出来。任何一层出问题都不会污染事实。

## 2. 事实层：事件日志

### 2.1 事件的物理形态

```
RunEvent {
  runId, seq,                 // 主键 (runId, seq)；seq 严格单调
  atMs,                       // 墙钟，仅用于展示
  kind,                       // 封闭枚举（见 03 §6.1）
  entryId, caseId,            // 归属（可空，run 级事件无归属）
  payload                     // 小写 JSON；大载荷只存引用
}
```

三条不可违背的纪律：

1. **append-only**：事件永不 update、永不 delete。撤销一次运行不是删除，而是再写一条 `run_voided` 事件。
2. **大载荷外置**：`payload` 只放小字段（status / 数值 / 短字符串）；响应体等大对象落 `artifact` 表或文件，`payload` 里只留 `sha256` + 引用 id。理由：事件日志要能整段扫读（重判时全量读），不能被 MB 级报文拖垮。
3. **写时脱敏**：任何进入 `payload` 的字符串在**写入前**执行脱敏（token / 手机号 / 邮箱 / 身份证 / 银行卡）。理由见 [08](08-安全基线.md)——日志会被导出和分享，写入即无法收回。

### 2.2 事件必须自足

一条硬性要求：**从事件日志单独出发，不读任何其他表，就能完整重算出所有 verdict。**

这意味着事件里必须包含判定所需的一切：

| 判定需要 | 事件从哪来 |
|---|---|
| 期望值 | `assert_evaluated` 事件里带 `expected`（**不能只存 assertId 然后去查用例表**） |
| 严重度 | 同上，带 `severity` |
| 实际值 | 同上，带 `actual` |
| 判定策略 | `run_started` 里带策略快照（**不能引用"当前项目设置"**） |
| 重试历史 | `retry_scheduled` + 多次 `entry_finished` |
| 提取的变量 | `var_extracted` |

**"不能只存 id 再去查"** 是这里最容易被违反的一条。看起来冗余（expected 明明在用例里存着），但一旦用例被人工修改过，历史运行的判定就会**跟着变**——那就等于事实可以被追溯地篡改。冗余存储期望值，是**快照语义**，代价是存储，收益是历史不可变。

### 2.3 判定策略快照

`run_started` 事件携带**当次运行使用的完整策略**：

```
RunPolicy {
  version: 1,
  failOnSeverity: "major",          // 此级别及以上失败 → failed
  degradedOnSeverity: "minor",      // 此级别失败 → degraded
  retry: { maxAttempts, on, backoff, jitter },
  flakyDetection: { enabled, windowSize },
  timeoutMs, concurrency,
  ignoreCaseIds: number[],          // 已知豁免
  scriptTimeoutMs
}
```

**为什么快照而不引用**：如果策略是"项目的当前设置"，那么任何人改设置都会**追溯改变所有历史运行的结论**。快照让每次运行固化自己的判定语境。要应用新规则，走 §5 的显式重判。

### 2.4 事件的完整性校验

每个 run 的结束事件带 `eventCount` 与末事件 `sha256` 摘要：

```
run_finished { status, counters, eventCount, chainHash }
```

`chainHash` = 对所有事件按 seq 依次哈希的累积值。用途：

- 检测日志被意外截断（`eventCount` 不符）
- 检测日志被篡改（`chainHash` 不符）
- 导出/导入归档时验证完整性（前稿 M6 "便携包"需要这个）

不是密码学级防篡改（本地应用，威胁模型是**误操作**而非对手攻击），但足以让"日志是不是完整的"变成一个可回答的问题。

## 3. 判定模型

### 3.1 verdict 的取值

六个值，每个都有明确且不重叠的含义：

| verdict | 含义 | 判定条件 | 界面上 |
|---|---|---|---|
| `passed` | 通过，且稳定 | 所有 blocker/critical/major 断言通过，无 flaky 迹象 | 绿 |
| `degraded` | 功能对，但有次要问题 | 仅 minor 断言失败 | 黄 |
| `failed` | 被测对象不符合预期 | 有 blocker/critical/major 断言失败（且重试耗尽） | 红 |
| `errored` | **未能完成测试** | 连接失败 / 超时 / 脚本异常 / 环境错误 | 灰 |
| `flaky` | 通过但不可信 | 多次尝试结果不一致，末次通过 | 紫 |
| `skipped` | 未执行 | 被取消 / 依赖失败 / 显式跳过 | 暗灰 |

**两个中间态的存在理由再强调一次**（03 §2.6 已述，此处从结果侧重述）：

- **`degraded` 保护通过率的可信度**。把"少了可选字段"和"返回 500"都算失败，团队会学会忽略红色。分级后 `passed` 重新意味着"真的没问题"。
- **`errored` 保护被测对象的名誉**。连不上服务不算"服务有 bug"。混淆二者会污染趋势判断，且这种污染一旦进入历史就很难纠正。

### 3.2 判定是纯函数

```
verdict = reduce(events, policy)

输入：该 run 的全部事件（按 seq 排序）+ 策略快照
输出：RunVerdict { perEntry[], perCase[], perRun, flakySet }

约束：
  · 不读时钟          （时间只能来自事件里的 atMs）
  · 不读网络          （一切观测都在事件里）
  · 不使用随机        （同一输入必然同一输出）
  · 不读其他表        （事件必须自足，§2.2）
```

**为什么"不读时钟"很重要**：一个自然的冲动是"如果运行超过 30 分钟就算超时"。但如果判定读当前时间，那么重跑判定会得到不同结果——**历史结论就变成了"什么时候算"的函数**。正确做法是超时也在执行期判定并发成事件（`entry_errored { reason: timeout }`），判定层只读事件。

### 3.3 entry → case → run 的折叠

判定按三层折叠，每层规则明确：

**第一层：entry 判定**

```
对某个 entry 的所有事件：
  · 有 step_errored(host_crash)        → errored
  · 有 assert_evaluated(passed=false) 且 severity ≥ failOnSeverity
        且所有 attempts 都失败          → failed
  · 有 assert_evaluated(passed=false) 且 severity = degradedOnSeverity
                                        → degraded
  · 首次尝试失败但后续成功              → passed（并记入 flaky 候选）
  · 全部通过                            → passed
  · 被取消                              → skipped
```

**第二层：case 判定（多参数行折叠）**

```
case 的 verdict = 其所有 entry 的最严重值
严重度排序：errored > failed > flaky > degraded > skipped > passed
```

**这里的一个设计选择**：`skipped` 排在 `passed` 之前但低于 `degraded`。理由：一个用例的部分参数行被跳过，不应报告为"通过"（会掩盖未覆盖），但也不应报告为"失败"（没测）。**"部分跳过"是真实状态**，不该被折叠掉——报告里显示 `degraded` 并注明"3/5 参数行已执行"。

**第三层：run 判定**

```
run.status（completed/errored/cancelled）与 run 的通过情况是两件事：
  · status 描述"跑完没有"（03 §4.1）
  · 通过率描述"跑得怎么样"

run 的汇总计数是投影：
  counters = count(case_result by verdict)
  不存字段，查询期算（P2）
```

### 3.4 flaky 的判定

```
flaky 判定（策略可配）：
  entry 的多次尝试结果不一致（有 pass 有 fail）
    → verdict = passed（末次为准）
    → flaky = true

  entry 多次尝试都是失败，但失败原因不同（如一次 connect_failed 一次 assert_failed）
    → verdict = failed
    → flaky = true（标记为"不稳定失败"，值得单独看）
```

**`flaky` 为什么不是独立 verdict 而是标记位**：

如果把 flaky 做成第七个 verdict，就丢掉了"它最终是通过还是失败"这个信息。作为标记位，可以同时表达"末次通过 + 历史上不稳定"，界面上是紫色，可单独筛选，趋势图上单列一条曲线。

**窗口聚合**：单个 run 内的 flaky 只是线索；真正的 flaky 判断需要**跨运行**——同一 case 在最近 N 次运行中时通时不通。这是查询期派生：

```sql
-- 稳定性榜（查询期算，不落表）
SELECT case_id,
       COUNT(*) AS runs,
       SUM(CASE WHEN verdict = 'passed' THEN 1 ELSE 0 END) AS passes,
       SUM(CASE WHEN flaky THEN 1 ELSE 0 END) AS flaky_runs
FROM case_result
WHERE project_id = :pid AND run_id IN (最近 N 次 run)
GROUP BY case_id
HAVING flaky_runs > 0
ORDER BY flaky_runs DESC;
```

### 3.5 判定的可测试性

因为判定是纯函数，它可以被**穷举测试**：

```
给定事件序列 → 期望 verdict
  · 空事件 → errored(incomplete)
  · 只有 run_started → errored(incomplete)
  · 事件乱序（seq 跳过）→ errored(corrupt)
  · 一次 pass → passed
  · fail 后 pass → passed + flaky
  · 三次 fail → failed
  · minor fail → degraded
  · connect_failed → errored（不是 failed）★
  · 被跳过 → skipped
  · chainHash 不符 → errored(corrupt)
```

**这是"判定纯函数"最大的工程红利**：判定逻辑的测试不需要网络、不需要数据库、不需要等待。上百个边界用例毫秒级跑完。

★ 标记的那条是最重要的一个测试：**"连不上服务"必须判 errored**。它是 P4 与 §3.1 的联合体现。

## 4. 展示层：一切都是投影

### 4.1 投影清单

| 展示物 | 计算方式 | 何时算 |
|---|---|---|
| 运行通过率 | `passed+degraded / total`（可选口径） | 列表查询期 |
| 用例矩阵（用例 × 运行） | 交叉查询 | 视图期 |
| 趋势曲线 | 按时间聚合 run | 查询期（窗口函数） |
| 慢用例榜 | `ORDER BY durationMs DESC` | 查询期 |
| 不稳定榜 | §3.4 的窗口聚合 | 查询期 |
| 原则触发率 | 从 `assert_evaluated` 的 `principleId` 聚合 | 查询期 |
| 未覆盖接口 | `route LEFT JOIN case WHERE case IS NULL` | 查询期 |
| 覆盖率 | `已有用例的 route 数 / 总 route 数` | 查询期 |

**没有一个需要落聚合表。** 这是 P2 的完整兑现。

### 4.2 通过率的口径必须显式

"通过率 92%" 可以有至少四种算法，结论差别很大：

| 口径 | 公式 | 适用 |
|---|---|---|
| 严格 | `passed / total` | 质量门禁（degraded 也算不达标） |
| 宽松 | `(passed + degraded) / total` | 日常观感 |
| 排除出错 | `passed / (total - errored)` | **评估被测对象质量**（环境问题不该算它头上） |
| 用例级 | 按 case 而非 entry 聚合 | 与测试用例数对齐 |

**设计决策：口径是显式选项，UI 上必须标出当前用的是哪个。** 显示"92%" 而不说口径，等于给了一个无法追问的数字——这违反本稿的基本立场。默认用"排除出错"，因为它最接近"被测服务的真实质量"这一意图。

### 4.3 结果的可解释性：从数字追问到证据

每个显示的数字都必须能**三步追问到证据**：

```
通过率 92%
  → 点开：37 个 failed（列表）
    → 点开某个：断言 actual=50001, expected=400, source=order.controller.ts:88
      → 点开：完整请求/响应报文 + 这是第 3 次尝试（前两次 connect_failed）
```

**第 3 层要能回答"为什么这个值算对"**：`expected=400` 的依据是什么？→ 溯源到 `Principle { rule: "金额超限拒绝", source: "order.controller.ts:88" }`，并且可以点开跳到源码。

这是 deepStudio「点击节点 → 定位到 MBT 源码行」的同一手法，用在了测试结果上。

## 5. 重判（Re-judge）：让结论可以进化

### 5.1 为什么需要

真实场景里，判定规则会变：

- 团队决定"响应头缺 X-Request-Id"不再算失败（降为 info）
- 发现某接口的超时阈值设错了，应该从 5s 放宽到 15s
- 引入了新的 flaky 检测窗口
- 发现之前把 `errored` 错算成了 `failed`（口径 bug）

**传统做法**：改规则 → 重跑所有测试 → 得到新数据。代价是时间、环境、以及**历史不可比**（代码也可能变了，分不清是规则的功劳还是代码的）。

**本稿做法**：改规则 → 对历史事件重算 verdict → 数据不变、结论更新。可以立刻回答"如果当初用这个规则，结果会怎样"。

### 5.2 重判的机制

```
Rejudge {
  projectId,
  scope: { runIds } | { caseIds } | { timeRange },
  policy: RunPolicy,              // 新策略
  mode: "preview" | "apply"
}
```

- **preview**：算出新结论，与旧结论做 **diff**，展示"37 个 failed 中有 5 个会变成 degraded，2 个 errored 会变成 passed"，**不写任何东西**
- **apply**：把新判定写入 `case_result` 投影（覆盖投影，**事件日志不动**），并写一条 `rejudged` 事件记录"谁在何时用了什么策略重判了哪些运行"

**"事件日志不动"是关键**：重判只改投影。这意味着重判本身也是可撤销的——用旧策略再重判一次即可回到原状。

### 5.3 重判与对账（Diff）是同一机制

同一个 diff 引擎服务两个场景：

**场景 A：策略重判**（同一批事件，两套策略）
```
"如果把 minor 降为 info，通过率从 92% → 95%"
```

**场景 B：两次运行对账**（两批事件，同一套策略）
```
run #128 (今天) vs run #127 (昨天)
  · 新失败 3 个    ← 可能是本次代码变更引入
  · 新通过 5 个    ← 修复生效
  · 从 flaky 转稳定 2 个
  · 从稳定转 flaky 1 个  ← 需要关注
```

**场景 B 是 API 测试最有价值的能力之一**：它把"测试"从"看红绿灯"变成"看变化"。单次通过率 92% 不说明什么，但"从 96% 掉到 92%，新增 3 个失败且都在订单接口"是明确的行动信号。

diff 的输出结构：

```
RunDiff {
  baseRunId, headRunId,
  newFailures: CaseRef[],       // 新增失败（最高优先级）
  fixedCases: CaseRef[],        // 由失败转通过
  newlyFlaky: CaseRef[],
  stabilizedCases: CaseRef[],
  verdictChanged: { case, from, to }[],
  durationDelta: { medianMs, p95Ms, direction }
}
```

**排序原则**：`newFailures` 永远排最前。修复了的和一直失败的都不是当务之急，**新出现的失败才是**。

### 5.4 重判的边界

不可重判的情况（明确列出，避免误用）：

| 情况 | 原因 |
|---|---|
| 事件日志不完整（`chainHash` 不符） | 事实本身可疑，重判无意义 |
| 策略需要事件里没有的信息 | 例如新策略要读完整响应体，但当时按阈值外置了且 artifact 已被保留策略清理 |
| 跨 schema 版本 | 事件格式变更后，旧事件可能缺新字段；需迁移器（见 06） |

**第 2 条会真实发生**：如果新策略需要看原始响应体，而 artifact 已被清理（保留策略），就无法重判。**缓解措施**：`RunPolicy` 里可以声明 `requiresFullArtifacts: boolean`，执行期据此决定是否强制保留全部 body。**代价前置**比事后发现不能重判要好。

## 6. 人工介入的结果语义

运行可以暂停、可以标注、可以豁免。这些人工动作也必须**成为事件**，否则它们就成了日志之外的隐性知识。

### 6.1 人工动作即事件

| 动作 | 事件 | 语义 |
|---|---|---|
| 暂停 / 恢复 | `run_paused` / `run_resumed` | 中间可能有环境变更（如重启了服务），判定时可见 |
| 标注 | `note { text }` | 提供上下文，不改变 verdict |
| 豁免某用例 | `case_waived { caseId, reason, by, expiresAt }` | 该 case 判 `skipped(waived)`，不计入通过率**分母**，但单列显示 |
| 手动改判 | `case_overridden { caseId, from, to, reason, by }` | **极其慎用**：人为覆盖判定。必须记录谁、为什么 |
| 作废整个 run | `run_voided { reason, by }` | 该 run 从所有统计中排除（如"跑在了错误的环境上"） |

### 6.2 豁免 vs 覆盖：必须区分

这两个动作很容易被混为一谈，但语义完全不同：

| | 豁免（waive） | 覆盖（override） |
|---|---|---|
| 含义 | "这个测试暂时不该跑/不算数" | "这个测试的结果不对，我认为是 X" |
| 典型场景 | 已知缺陷，等修复；功能已下线 | 环境特殊，判定规则不适用 |
| 对分母 | **不计入**分母 | 计入分母，但改判定结果 |
| 是否影响通过率 | 不影响（既非通过也非失败） | **影响** |
| 危险度 | 低（透明） | **高（可能掩盖真实问题）** |

**默认只提供豁免，覆盖需要二次确认 + 强制填写理由**。理由：豁免是诚实的（"没测"是明确状态），覆盖是可能自欺的（"我判断它是好的"）。

`expiresAt` 是豁免的关键字段——**豁免必须过期**。永不过期的豁免会变成永久性的沉默，是技术债最隐蔽的形式。界面要在豁免到期前提醒。

### 6.3 人工动作对重判的影响

暂停/恢复/标注/豁免/作废**都是事件**，因此重判时一并参与计算（判定函数读事件时自然读到）。但**覆盖（override）特殊**：它是人的意志而非可推导的规则，重判时**保留覆盖**（不因策略变化而被冲掉），并在 diff 中标注"此 case 的结果来自人工覆盖，未参与自动重判"。

## 7. 归档与保留

### 7.1 三层保留策略

不是所有数据都值得永久保留。分三层，各自策略：

| 层 | 内容 | 默认保留 | 可配 |
|---|---|---|---|
| **事件** | `run_event` | **永久**（体积小） | 否——这是真源 |
| **投影** | `case_result` / `step_result` | 永久（可从事件重建，但重建慢） | 是（删了可重建） |
| **artifact** | 报文 body / 大对象 | **90 天**，或按"失败的永久保留" | 是 |

**artifact 的策略值得细说**：

```
保留规则（默认）：
  · failed / errored 的 artifact   → 永久保留（这些是排查依据）
  · passed 的 artifact             → 90 天
  · 超过阈值的大 body（>10 MB）     → 只保留前 64 KB + sha256
```

**"失败的永久保留"** 是关键决策：失败报文是排查问题的唯一证据，删掉就再也说不清当时发生了什么。而通过的报文价值随时间快速衰减。

**这与重判的冲突**（§5.4）在此缓解：默认只清理通过用例的大报文，而失败用例的完整保留——重判最需要看的恰恰是失败的。

### 7.2 归档浏览器（只读，呼应 P1/前稿 ddpView 的先例）

提供一个**只读**的历史查看器，能力与限制明确：

**能做的**：
- 按时间 / 项目 / 接口 / 会话 / 标签检索历史运行
- 回放一次运行：按 seq 顺序重播事件，界面逐步重现（前稿 §6 "按 Agent 会话回放"的落地）
- 重判（只改投影，§5.2）
- 导出报告（JSON / CSV / Markdown）

**不能做的**（与 deepStudio 的 `ddpView` 同一纪律）：
- 不触发执行
- 不修改用例
- 不删除事件
- 不调用 Agent

**回放的价值**：新人接手时，可以"看"一次真实运行是怎么跑的；排查间歇性问题时，可以逐事件看第 3 步和第 4 步之间到底发生了什么。这是纯静态报告给不了的。

### 7.3 导出

导出不是"把表 dump 出来"，而是**从事件日志生成一份自足的报告**：

| 格式 | 内容 | 用途 |
|---|---|---|
| JSON | 完整事件日志 + 判定结果 + 策略快照 | 机器消费、跨系统对账 |
| CSV | 用例级结果表 | 表格分析 |
| Markdown | 人读摘要：通过率、新失败、慢用例、不稳定项 | 贴到 PR / 周报 |
| HTML | 自包含报告（含关键报文片段） | 分享给非工具使用者 |

**导出的报告必须自带策略快照与事件数**，否则脱离工具后无法判断口径——一份不知道用什么规则算出来的"通过率 92%"是没有意义的。

## 8. 与前稿的差异小结

| 前稿 | 本稿 |
|---|---|
| "留痕三件套"（HTTP 留痕 / AI 请求档案 / 溯源块） | **三层分离：事件事实 / 判定 / 展示投影** |

| 无 flaky 概念 | **flaky 一等标记 + 跨运行聚合** |

| 无历史对比 | **RunDiff：新失败 / 已修复 / 新不稳定 / 已稳定** |
