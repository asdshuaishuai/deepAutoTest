# 02 · 架构与进程模型

> 技术选型的推导见 [10-技术选型.md](10-技术选型.md)。本文只讲结构。
>
> **核心约束**：系统 WebView 的 `show()` 会阻塞 Node 事件循环（[10 §2.3](10-技术选型.md#23-实测发现的硬约束show-阻塞-node-事件循环)）。
> 因此架构的**第一原则是"主线程不做 IO"**——所有异步操作必须在 Worker 线程里执行。

---

## 1. 三层结构（两个进程）


## 2. ★ 主线程为什么不能做 IO（本方案的架构基石）

### 2.1 实测结论

调用 `Webview.show()` 后，Node 主线程进入系统 WebView 的原生主循环：

```
[  125ms] 调用 show() 之前
（此后无任何日志 —— setInterval 不触发、fetch 不执行、await 不完成）
```

实测（`probe6.mjs`）进一步确认：**连 `async` 的 bind 回调都会挂起**——日志停在 `asyncCall(2) 开始`，Promise 永不 resolve。

**原因**：`show()` 占用 Node 的事件循环（Cocoa run loop），Promise 微任务、定时器、IO 完成回调全部无法调度。

### 2.2 后果对照

| 操作 | 在主线程 | 在 Worker |
|---|---|---|
| `fetch` / undici | ❌ 挂起 | ✅ 正常 |
| 数据库查询 | ❌ 挂起 | ✅ 正常 |
| `fs` 读写 | ❌ 挂起 | ✅ 正常 |
| `setInterval` | ❌ 不触发 | ✅ 正常 |
| `await` 任意 Promise | ❌ 不完成 | ✅ 正常 |
| **`bind` 同步回调** | ✅ **可用**（原生层同步调用） | — |
| **`Atomics.wait`** | ✅ **可用**（不依赖事件循环） | — |

**最后两条是本方案能成立的唯一原因**：`bind` 让我们能在被阻塞的主线程里接收页面调用，`Atomics.wait` 让我们能同步等待 worker 结果。

### 2.3 跨线程通信的实现

```ts
// src/main/rpc-bridge.ts —— 主线程侧
const SAB_SIZE = 16 * 1024 * 1024;             // 16 MB 共享缓冲
const sab = new SharedArrayBuffer(SAB_SIZE);
const ctrl = new Int32Array(sab, 0, 4);        // [0]=状态 [1]=长度 [2]=序号 [3]=保留
const buf = new Uint8Array(sab, 16, SAB_SIZE - 16);

const CTL_IDLE = 0, CTL_REQ = 1, CTL_RES = 2;

// 同步调用 worker（主线程可安全使用的唯一方式）
export function callWorkerSync(req: string, timeoutMs = 30_000): string {
  const bytes = new TextEncoder().encode(req);
  if (bytes.length > buf.length) throw new Error('request_too_large');
  buf.set(bytes, 0);
  Atomics.store(ctrl, 1, bytes.length);
  Atomics.store(ctrl, 0, CTL_REQ);
  Atomics.notify(ctrl, 0);

  const r = Atomics.wait(ctrl, 0, CTL_REQ, timeoutMs);   // ★ 同步等待，不依赖事件循环
  if (r === 'timed-out') throw new Error('worker_timeout');

  const out = new TextDecoder().decode(buf.subarray(0, Atomics.load(ctrl, 1)));
  Atomics.store(ctrl, 0, CTL_IDLE);
  return out;
}

export function installRpc(w: Webview): void {
  // 主线程在此被 show() 的原生循环同步调用；自身不能 await，只能同步等待
  w.bind('rpc', (_wv, requestJson: string) => callWorkerSync(requestJson));
}
```

```ts
// src/worker/main.ts —— Worker 侧（有完整事件循环）
const ctrl = new Int32Array(workerData.sab, 0, 4);
const buf = new Uint8Array(workerData.sab, 16);

while (true) {
  Atomics.wait(ctrl, 0, CTL_IDLE, 60_000);          // 等待主线程请求
  if (Atomics.load(ctrl, 0) !== CTL_REQ) continue;

  const req = new TextDecoder().decode(buf.subarray(0, Atomics.load(ctrl, 1)));
  const res = await handleRpc(req);                  // ★ 这里可以自由 await
  const bytes = new TextEncoder().encode(res);
  buf.set(bytes, 0);
  Atomics.store(ctrl, 1, bytes.length);
  Atomics.store(ctrl, 0, CTL_RES);
  Atomics.notify(ctrl, 0);
}
```

**四条设计要点**：

1. **消息走 SAB，不走 `postMessage`** —— 后者依赖事件循环回调，主线程收不到
2. **`Atomics.wait` 双向使用** —— 主线程等 worker 结果，worker 等主线程请求，形成干净的同步 RPC
3. **超时必须有** —— `Atomics.wait` 的超时参数防止死等（worker 崩溃时主线程不能挂死）
4. **统一封装成 RPC 层** —— 业务代码不感知 SAB 细节（见 §4）

### 2.4 一个实现陷阱：静态服务必须在 worker 里

WebView 要加载前端产物（`navigate('http://127.0.0.1:PORT')`），而 **HTTP 服务需要在事件循环里处理请求**。主线程事件循环被 `show()` 占用，**在主线程起服务页面永远打不开**。

```
正确顺序：
① worker 启动 → 起静态服务 → listen 完成
② 主线程 Atomics.wait 确认服务就绪
③ 主线程创建 Webview → navigate(localhost:PORT)
④ 主线程 show()  （事件循环此后被占用，但服务在 worker 里正常工作）
```

## 3. 代码结构

```

├─ main/                       ① 主线程（薄壳）
│  ├─ index.ts                 启动顺序、窗口生命周期
│  ├─ rpc-bridge.ts            ★ SAB/Atomics 桥（§2.3）
│  └─ window.ts                Webview 创建、导航、应用内菜单
│
├─ worker/                     ② Worker（全部业务）
│  ├─ main.ts                  请求循环、RPC 分发
│  ├─ rpc-router.ts            方法路由表（类型安全的单一契约来源）
│  ├─ static-server.ts         ★ 本地静态服务（前端产物）
│  ├─ domain/
│  │  ├─ source/               接入与索引
│  │  ├─ adapters/             框架适配器（ts-morph）
│  │  ├─ principles/           原则提取器
│  │  ├─ sampler/              只读采样 + 脱敏
│  │  ├─ runner/               执行引擎 + 沙箱
│  │  ├─ judge/                ★ 判定纯函数（禁 IO）
│  │  ├─ agent/                libfx 封装
│  │  └─ urlguard/
│  └─ store/
│     ├─ db.ts                 SQLite 连接与事务
│     ├─ migrations/
│     ├─ repositories/         按领域（首参恒为 projectId）
│     └─ artifacts.ts
│
├─ renderer/                   ③ 前端（React）
│  ├─ api/rpc.ts               对 window.rpc 的类型安全封装
│  └─ ...
│
└─ shared/                     共享的纯类型（无实现）
```

**三条结构性纪律**（用 lint / 类型强制，不靠评审）：

1. **`main/` 禁止 import 任何 IO 模块**（`node:net` / `node:fs` / `undici` / 数据库驱动）。它只能碰 Webview API 与 SAB 桥。用 ESLint `no-restricted-imports` 保证。

2. **`worker/domain/judge/` 禁止 import 任何 IO 模块**（无 db、无 fs、无 net、无 `Date.now`）。这是 [04](04-结果模型.md) "判定是纯函数"在代码结构上的强制。

3. **`worker/store/repositories/` 的每个函数首参恒为 `projectId`**（或 `ProjectScope`）。这是 [01 P5](01-定位与原则.md#p5-项目即边界) "项目即边界"在类型层的强制——跨项目查询在编译期就写不出来。

## 4. RPC 契约

### 4.1 单一来源

```
src/worker/rpc-router.ts       ← 唯一真相：方法名 + 请求/响应类型
src/renderer/api/rpc.ts        ← 渲染进程的类型安全封装
src/shared/rpc-types.ts        ← 共享类型定义
```

```ts
// src/shared/rpc-types.ts —— 契约定义（示意）
export interface RpcMethods {
  'project:list':   { req: void;                                    res: Project[] };
  'project:create': { req: CreateProjectInput;                      res: Project };
  'run:start':      { req: { projectId: number; plan: RunPlan };     res: { runId: number } };
  'run:cancel':     { req: { runId: number };                       res: void };
  'run:rejudge':    { req: RejudgeInput;                            res: RejudgeDiff };
  'cases:list':     { req: { projectId: number; filter: CaseFilter }; res: CaseRow[] };
  'agent:prompt':   { req: AgentPromptInput;                        res: { turnId: number } };
  'push:poll':      { req: { sinceSeq: number };                    res: RunEventDto[] };
}
```

### 4.2 页面侧调用

```ts
// 页面里（前端）
const projects = await window.rpc('project:list');
```

`window.rpc` 由 `init(js)` 注入的一段极薄 shim 提供：

```js
// 主线程通过 w.init() 注入（在 window.onload 之前）
window.rpc = (method, params) =>
  rpcRaw(JSON.stringify({ method, params }))
    .then(s => { const r = JSON.parse(s); if (r.error) throw new Error(r.error); return r.result; });
```

### 4.3 ★ 实时推送：由页面轮询驱动

**问题**：worker 要主动推送运行中的事件流，但主线程事件循环被占用，无法接收 `postMessage`。

**解法：让页面来拉。** 渲染进程是**唯一有正常事件循环的地方**（它就是 WebView 的 JS 运行时）：

```js
// 页面侧
setInterval(async () => {
  const events = await window.rpc('push:poll', { sinceSeq });
  if (events.length) store.applyEvents(events);
}, 100);
```

主线程的 `push:poll` handler 只做一件同步的事：**从 SAB 读 worker 已写入的推送缓冲**。

**这个设计很干净**：

- 主线程不做任何异步（符合 §2 的约束）
- 页面有正常事件循环，轮询是自然的
- 实时性受轮询间隔限制（100ms 级）—— 对本产品完全够用（测试执行本身是秒级操作）

**保留自前一版的原则**：**先落库、再让推送可读**（[04 §1](04-结果模型.md#1-三层分离)）。轮询拿到的事件一定已持久化。

### 4.4 推送的 SAB 布局

推送数据量大且方向单一，用 SAB 里的**环形缓冲**：

```
SAB 布局（16 MB）：
┌─────────────┬──────────────────────────────────────────────────┐
│ ctrl (16B)  │  RPC 请求/响应缓冲 (4 MB)  │  推送环形缓冲 (12 MB)  │
│ 4×Int32     │                            │  (worker 写，主线程读)  │
└─────────────┴────────────────────────────┴──────────────────────┘
```

**溢出处理**：环形缓冲满时，worker **丢弃最旧的事件并置"溢出"标志**；页面轮询时发现该标志，**改走 `run:refetch` 全量重查**（因为丢弃意味着增量不完整）。这比阻塞 worker 更合理——UI 一致性由定期全量对账兜底（[05 §3.2](05-结果呈现.md#32-增量应用-定期对账)）。

## 5. Worker 池的组织

| Worker | 职责 | 为什么独立 |
|---|---|---|
| **core-worker** | RPC 主循环、领域逻辑、存储、静态服务 | 主业务 |
| **analysis-worker** | 源码索引与 AST 分析（ts-morph） | **CPU 密集**，会阻塞 core-worker 的事件循环 → 拖慢所有 RPC |
| **assert-worker** | 断言脚本执行 | **不可控代码**，必须可强制 `terminate()` |
| **Agent（子进程）** | libfx | 见下 |

**为什么 AST 分析要单独 worker**：分析一个万文件仓库可能耗时数十秒。若与 RPC 循环同线程，**整个界面会卡住**（所有 RPC 排队等待）。

**为什么断言沙箱要单独 worker**：`node:vm` 的 `timeout` 对某些死循环无效，**只有 `worker.terminate()` 能可靠杀死**（[08 §6](08-安全基线.md#6-断言脚本沙箱)）。

### 5.1 Agent 用子进程而非 worker

| 方案 | 优点 | 缺点 |
|---|---|---|
| worker 内 `require('libfx')` | 简单，无额外 IPC | N-API 在 worker 的兼容性待验证；Agent 崩溃会拖垮 core-worker |
| **独立 child_process** | **完整事件循环、天然隔离、崩溃不影响主流程** | 需 stdio IPC（但只有 Agent 一路，量小） |

**建议直接用 child_process**：

1. **风险最低** —— 子进程行为与普通 Node 无异（无需担心 worker + N-API 的组合问题）
2. **天然隔离** —— Agent 崩溃、流式阻塞、内存泄漏都不影响测试执行
3. **代价很小** —— stdio JSON lines 序列化，而 Agent 交互频率很低（一轮对话几条消息）

**这也让待验证项 W1 的风险可控**：即使 worker 方案完全不可行，子进程这条路是确定可行的。

## 6. 崩溃与错误处理

| 故障 | 检测 | 处理 |
|---|---|---|
| **analysis-worker 崩溃** | `worker.on('error')` | 该索引任务标记失败，可重试；UI 提示 |
| **断言脚本死循环** | 超时 | `terminate()` 后判 `errored(script_timeout)`，**run 继续** |
| **core-worker 崩溃** | `worker.on('error')` | 主线程重启 worker；**已提交事件都在 SQLite**，重连后恢复 |
| **Agent 子进程退出** | `child.on('exit')` | 显示原因；**不影响其它功能**（[07 §1.4](07-Agent与人机门.md#14-agent-不可用时的降级)） |
| **目标服务不可达** | undici 抛错 | 该 case 判 `errored(connect_failed)`，**不是 failed**（[04 §3.5](04-结果模型.md#35-判定的可测试性) ★） |
| **`Atomics.wait` 超时** | 返回 `timed-out` | 抛 `worker_timeout`，页面收到错误；**主线程不挂死** |
| **页面加载失败** | 页面主动 `rpc('app:ready')` 未在超时内到达 | 显示诊断提示（见 §8） |

**"core-worker 崩溃可恢复"依赖事件日志**：worker 重启后界面重连并重新查询——已提交事件都在库里，显示的是真实进度（[04 §1](04-结果模型.md#1-三层分离) 的直接红利）。

## 7. 安全边界

**本方案在隔离上有一个结构性优势**：

| 维度 | Electron | 本方案 |
|---|---|---|
| 页面访问 Node | 靠配置关闭（`nodeIntegration: false` + `contextIsolation: true`） | **结构上不可能**——从未向页面注入任何 Node 能力 |
| 配置错误的风险 | 有（配错就是 RCE 面） | **无**（没有可配错的开关） |
| 恶意源码触发 XSS 后 | 若配置错误可升级为 RCE | 最多是页面内脚本执行，**无法触及文件系统/进程** |

**但仍须遵守的纪律**：

1. **不可信输入必须转义**（[05 §1.3](05-结果呈现.md#13-不可信输入必须转义)）—— 被测源码、数据库内容、API 响应都会进页面
2. **严禁 `dangerouslySetInnerHTML`**；代码高亮用转义库（Shiki / CodeMirror）；Markdown 用 `rehype-sanitize`
3. **RPC 方法白名单** —— `bind('rpc')` 只暴露 `RpcMethods` 里声明的方法，未知方法拒绝
4. **本地静态服务仅监听 loopback**，并校验 `Host` 头（防 DNS rebinding 到本机服务）

### 7.1 RPC 入参必须做运行时校验

页面是"半可信"的（可能被 XSS 注入）。**TypeScript 类型在运行时不存在**，必须校验：

```ts
const handlers: { [K in keyof RpcMethods]: (req: RpcMethods[K]['req']) => Promise<RpcMethods[K]['res']> } = {
  'project:create': async (input) => {
    const parsed = CreateProjectInputSchema.parse(input);   // ★ 运行时校验，不只是类型断言
    return projects.create(parsed);
  },
};
```

## 8. 启动顺序（容易出错的细节）

```
① 主线程：创建 Worker（传入 SAB）
② worker：起静态服务（listen 完成）→ 开 SQLite → 设置 ctrl[0] = READY
③ 主线程：Atomics.wait 确认就绪（带超时，如 10 秒）
④ 主线程：创建 Webview → size/title → bind('rpc') → init(shim) → navigate(localhost:PORT)
⑤ 主线程：show()  ← 阻塞，进入原生主循环
```

| 失败点 | 行为 |
|---|---|
| worker 未在超时内就绪 | 显示原生错误对话框，退出 |
| 静态服务端口被占 | worker 内换端口并回报实际端口（**不要写死**） |
| **页面加载失败** | **`webview` 库没有"加载失败"回调** → 必须让页面主动 `rpc('app:ready')` 上报；主线程超时未收到则显示诊断（"前端资源加载失败，请检查本地服务"） |

**最后一条是实际的坑**：`webview` 库不提供加载状态回调。**必须让页面主动上报就绪**，否则页面白屏时主线程毫无感知。

| 适配器 | Vitest + fixture 仓库 | 路由提取准确率（M1 出口 ≥90%） |
| 原则提取 | Vitest + fixture | 各校验库覆盖率 |
| runner | Vitest + 真实 mock server | 请求构造、断言求值、重试、超时、取消 |
| 仓储 | Vitest + 内存 SQLite | 项目隔离（跨 pid 查询返回空） |
| RPC 契约 | Vitest | 方法白名单、入参校验、错误映射 |
| **界面** | **Vitest + Testing Library** | 组件行为、派生函数 |
| 跨层集成 | 通过 `bind` 注入测试驱动 | 页面 ↔ Node RPC |

**★ 无法做浏览器级 E2E**（[10 §4.5](10-技术选型.md#45-测试与打包)）：系统 WebView 没有标准自动化协议。这是本方案的代价之一，**必须在 M1 明确，不能等到 M5 才发现**。

**补偿措施**：把"端到端"拆成两段可测的部分——前端用 Testing Library 测组件，RPC 层在 node 环境测 handler，二者通过共享的 `shared/rpc-types.ts` 保证契约一致。

**最有价值的两项**（因架构选择而变得容易）：

1. **判定纯函数测试**：上百个边界场景，无需网络/数据库/等待
2. **投影重建测试**：证明"事件日志为真源"不是口号。**必须在 M1 建立**（[06 §4.1](06-数据模型.md#41-投影必须可从事件重建)）

## 10. 构建与分发

| 项 | 方案 |
|---|---|
| 前端构建 | Vite → 静态产物（打包进分发包） |

## 11. 小结

| 维度 | 本方案 |
|---|---|
| 层数 | **3 层（主线程 / Worker / WebView）· 2 个进程** |
| 主线程职责 | **仅 UI 壳**（无 IO、无异步） |
| 跨线程通信 | **SAB + Atomics**（同步，因事件循环被占） |
| 跨进程通信（页面↔Node） | **webview `bind` + 手工 RPC 路由** |
| 实时推送 | **页面轮询 SAB**（页面有正常事件循环） |
| 隔离 | **结构性**（页面无 Node 能力，不可配置错误） |
| 测试 | **无浏览器级 E2E**（系统 WebView 无自动化协议） |

**保留自前一版的关键设计**（与栈无关）：

1. 事件日志为真源、判定纯函数、可重判（[04](04-结果模型.md)）
2. `failed` 与 `errored` 严格区分；`degraded` 中间态；`flaky` 一等（[04 §3](04-结果模型.md#3-判定模型)）
3. `judge/` 禁 IO、`repositories/` 首参 `projectId`（§3 的三条 lint 纪律）
4. 先落库、再推送（[04 §1](04-结果模型.md#1-三层分离)）
