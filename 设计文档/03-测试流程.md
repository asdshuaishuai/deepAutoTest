# 03 · 测试流程

> ★ 本次设计的重点章节之一。
> 前稿把执行压缩在 S6「执行与归档」一段里，只提了 runner + 断言沙箱 + 留痕三件套。
> 本文把「一次运行从被触发到归档」的完整生命周期展开，并回答一个前稿没问的问题：
> **测试用例到底是什么？**——不是"一次 HTTP 调用"，而是一条**可参数化、可组合、可判定**的执行小计划。
> 结果如何建模、如何呈现，分别见 [04](04-结果模型.md) 与 [05](05-结果呈现.md)。

---

## 1. 流程全景

六阶段管线（与前稿一致，projectId 贯穿全程）：

```
S1 源码接入 ──► S2 API 发现 ──✋──► S3 原则提取 ──✋──► S4 测试库采样
                                                            │
              S6 执行归档 ◄── ✋ S5 用例合成（fx Agent）◄────┘
     ✋ 人工确认门
```

**本文聚焦 S6 的内部结构**，但它与前序阶段的耦合点必须说清：

| 上游 | 提供给 S6 的东西 | S6 如何使用 |
|---|---|---|
| S2 API 发现 | `RouteCandidate`（method / path / handler 位置 / 框架 / 置信度） | 决定用例打向哪个 endpoint |
| S3 原则提取 | `Principle`（subject / rule / value / **source: file:line**） | 决定什么值算合法、什么值算边界 |
| S4 数据采样 | 真实样本行（已脱敏）+ 分布统计 | 提供**形态**（真实手机号长什么样、真实订单号前缀） |
| S5 用例合成 | `TestCase` 草稿（proposed，带溯源） | 待执行对象 |
| S1 源码索引 | 根路径、git ref | 溯源跳转的锚点 |

**S6 不只消费用例，它回写三类东西**：运行记录（事实）、判定（结论）、反馈（哪些原则真正用上了、哪条原则从没被违反过——后者是**原则本身的测试价值指标**，见 §7.4）。

## 2. 测试用例模型

### 2.1 用例不是"一次 HTTP 调用"

前稿的输出契约是：

```
{ cases: [{ name, params:{path,query,header,body}, expectedStatus, script }] }
```

这个形状**能表达"发一个请求看状态码"**，但表达不了真实测试需要的东西：

| 真实测试需求 | 前稿能否表达 | 问题 |
|---|---|---|
| 列表接口要先有数据才有意义 | ❌ | 无法表达前置步骤 |
| 用上一步返回的 id 请求详情 | ❌ | 无法在步骤间传值 |
| 金额恰好 50000 应通过，50001 应拒绝 | ⚠️ 很勉强 | 一个 case 一组参数，边界要拆成两个 case 就丢失了"这是一对边界"的语义 |
| 同一输入跑 5 次看是否稳定 | ❌ | 无法表达重复 |
| 先登录拿 token，后续都用它 | ❌ | 无环境/凭据概念 |
| 这个断言失败是可容忍的（已知缺陷） | ❌ | 无豁免概念 |

**本稿的用例模型**：用例是一棵**步骤树**，不是一组参数。

### 2.2 Case 结构

```
TestCase {
  id, projectId, name, description,
  routeId,                    // 对应哪条 API 候选
  status,                     // proposed | adopted | rejected（P3）
  provenance,                 // 溯源：引用的原则 + 真实样本（见 §2.5）
  steps: Step[],              // 有序步骤（本文核心）
  params: ParamSet,           // 参数化：同一用例的数据变体（见 §2.3）
  policy: EvalPolicy,         // 判定策略覆盖（见 04）
  tags, createdAt, proposedBy, reviewedBy
}
```

### 2.3 参数化：一组用例 = 一次运行的多条记录

参数化不是"生成 N 个用例"，而是**一个用例带一组数据变体**。区别很重要：边界值成对出现（`49999/50000/50001`）的语义是"验证这个边界"，拆成 3 个独立用例后这层语义就丢了，报表里也只是 3 行无关联数据。

```
ParamSet {
  kind: "single" | "boundary" | "pair" | "matrix" | "sequence",
  rows: ParamRow[]            // 每个 row 是一次执行的数据
}

ParamRow {
  label,                      // "金额=50000（边界内）"
  values: Record<string, Value>,
  intent: "baseline" | "boundary_low" | "boundary_high" | "invalid" | "empty" | "malformed" | "extreme"
}
```

`intent` 是关键字段——它让报告能说"**该接口的 4 个边界值中有 1 个未按预期拒绝**"，而不是"6 个用例失败了 1 个"。

**五种参数集的来源**：

| kind | 用于 | 数据来源 |
|---|---|---|
| `single` | 冒烟、单点验证 | Agent 合成 |
| `boundary` | 数值/长度/日期边界 | **S3 原则的 value**（`amount ≤ 50000` → `49999/50000/50001`） |
| `pair` | 成对反例（合法+非法） | 原则 + 采样分布 |
| `matrix` | 多字段组合 | 原则笛卡尔积（**需配上限**，防止组合爆炸） |
| `sequence` | 幂等/顺序依赖 | 需要多步骤，与 steps 配合 |

**矩阵爆炸的硬约束**：`matrix` 必须声明 `maxRows`（默认 32，上限 256），超限时**不截断而是报错**并要求人工缩小维度——静默截断会让人误以为覆盖完整。这条约束的理由是测试的信任基础：**"测过了"必须是真话**。

### 2.4 Step 模型

```
Step {
  id, caseId, seq,
  kind: "request" | "extract" | "assert" | "wait" | "script" | "db_check",
  ...
}
```

六种步骤类型，够表达真实测试，又不会变成通用编程语言：

| kind | 作用 | 关键字段 |
|---|---|---|
| `request` | 发一次 HTTP | method / url（模板）/ headers / body / timeout / followRedirects / tls 选项 |
| `extract` | 从上游响应取值，供后续步骤引用 | source（body_json / header / status）/ 表达式 / 变量名 |
| `assert` | 断言 | 目标 / 操作符 / 期望值 / **severity**（见 §2.6） |
| `wait` | 等待（异步接口、限流退避） | ms 或条件轮询（最大等待 + 间隔） |
| `script` | 复杂逻辑逃生舱 | JS 源码，沙箱执行（见 §5.4） |
| `db_check` | 侧证：查测试库验证副作用 | 连接 / 只读查询 / 期望（如"订单表新增 1 行"） |

**为什么有 `db_check`**：很多接口"返回 200"不代表真的写对了。订单接口返回成功但库里没有订单，是典型的**假通过**。`db_check` 让"响应"与"副作用"能同时对账，这是 API 测试里最容易被漏掉的一类验证。

**为什么有 `script` 但要克制**：真实项目总会有 DSL 表达不了的检查（签名校验、加密串格式、复杂时间窗口）。给一个逃生舱比逼用户放弃好；但它必须是沙箱化的、默认超时 5s、且**UI 上要有视觉区分**（`script` 步骤的失败比 `assert` 失败更难信任，因为它不可静态检查）。

### 2.5 溯源：每个用例必须能回答"凭什么是这样"

S5 合成的每个 case / 每个 step 都带 `Provenance`：

```
Provenance {
  principles: [{ principleId, source: "file:line", rule, usedAs }],   // 引用了哪条原则
  samples:    [{ table, pk, field }],                                 // 参考了哪条真实样本
  agentSession, agentTurn                                             // 哪个会话的哪一轮产出
}
```

三种情况必须区分清楚（这决定审计价值）：

| 来源 | 含义 | 信任度 |
|---|---|---|
| 原则推导 | 边界值来自源码里的校验规则 | **高**——有 `file:line` 可查证 |
| 样本推断 | 值形态来自真实数据 | 中——真实但可能不代表约束 |
| Agent 臆测 | 既无原则也无样本支撑 | **低——必须标记出来** |

**`usedAs` 字段**：同一个值可能来自原则也可能来自样本。当二者矛盾时，**原则胜出并标记冲突待人审**（前稿已有此规则，本稿将其落为字段：`conflict: { principleValue, sampleValue, resolved: "principle" }`）。

**没有溯源的用例不是无效，但要显式标记** `provenance: { principles: [], samples: [] }` → UI 显示"无溯源"徽章。理由：审计的价值在于能区分"有依据"和"看起来有依据"，把无依据的混在一起等于放弃审计。

### 2.6 断言的严重度：区分"错了"与"不合预期"

```
severity: "blocker" | "critical" | "major" | "minor" | "info"
```

| 级别 | 含义 | 对 verdict 的影响 |
|---|---|---|
| `blocker` | 核心正确性（状态码、关键字段存在） | 失败 → `failed` |
| `critical` | 业务规则（金额上限、权限） | 失败 → `failed` |
| `major` | 数据完整性（字段类型、非空） | 失败 → `failed`（默认） |
| `minor` | 次要约定（可选字段、格式偏好） | 失败 → `degraded`（不算 failed） |
| `info` | 仅记录，永不失败 | 永不改变 verdict，只写事件 |

**为什么需要 `degraded` 这个中间态**：把"响应头少了 X-Request-Id"和"下单接口返回 500"都算作 failed，会让通过率失去意义——团队很快学会忽略红色。分级让通过率重新变成一个可信的数字，同时不丢失信息（`degraded` 在界面上是黄色，可筛选，进趋势图但不算失败）。

**`info` 级别的实际用途**：把观察到的值记录下来（如响应时间分布、返回的 id 范围），供后续分析，但不参与判定。这让"我想看看这个值"不必写成一个永不失败的假断言。

## 3. 执行计划

### 3.1 Plan 是编译产物

**用户不直接执行用例，执行的是计划。** 计划由用例集编译而来，编译期完成所有静态校验：

```
RunPlan {
  id, projectId, createdAt,
  source: { caseIds, filter, tagQuery },     // 从哪些用例来
  env: EnvRef,                               // 打向哪个环境（属于项目）
  entries: PlanEntry[],                      // 扁平化的可执行单元
  concurrency, retry, timeout, policy,
  seed                                        // 随机种子（可复现）
}

PlanEntry {
  entryId, caseId, paramRowLabel, stepSeq,
  dependsOn: entryId[],                      // 依赖（extract 链）
  group: string                              // 并发分组（同组串行）
}
```

### 3.2 编译期校验（防止跑到一半才发现用例是坏的）

| 检查 | 失败处理 |
|---|---|
| 所有 `extract` 引用的变量在被引用前已定义 | **拒绝编译**，指出步骤位置 |
| 变量引用无环（不允许 A 依赖 B 又依赖 A） | 拒绝编译 |
| `matrix` 行数 ≤ `maxRows` | 拒绝编译，要求缩小维度 |
| `request` 的 URL 模板变量都有来源 | 拒绝编译 |
| 目标 Env 存在且 `baseUrl` 通过 urlguard 检查 | 拒绝编译（SSRF 前置拦截） |
| `db_check` 的连接存在且标记只读 | 拒绝编译 |
| 参数化行数 × 步骤数 ≤ 计划上限 | 拒绝编译（防止误跑百万次） |

**"拒绝编译"而非"跳过"**：一个静默被跳过的步骤会让报告说谎。宁可跑不起来，不可跑出错的结果。

### 3.3 并发与隔离

```
Plan 编译 → 按 group 分组
        ↓
  ┌─────────────┬─────────────┬─────────────┐
  │ group A     │ group B     │ group C     │  ← 最多 concurrency 组并行
  │ 串行执行     │ 串行执行     │ 串行执行     │
  └─────────────┴─────────────┴─────────────┘
```

分组规则：

1. **有 `dependsOn` 的 entry 必须在同组且按序**
2. **同 `caseId` 的参数行默认同组串行**——因为共享 `extract` 变量，并行会串值
3. 无依赖的 case 可分配到不同组并行
4. **`db_check` 所在的 case 默认单独成组**——数据库侧证对并发写入敏感

**默认 `concurrency = 1`。** 理由：API 测试的并发很容易触发被测服务的限流/风控，产生假失败（这恰恰是前稿 §3 提到的"A 项目风控污染 B 项目"的同类问题，只是发生在运行内部）。并发是**显式优化**，不是默认行为，且界面要显示"本次运行并发度为 4"以免误判结果。

### 3.4 环境与凭据

`Env` 属于项目（前稿 §3.1 已定）：

```
Env {
  id, projectId, name, baseUrl,
  variables: Record<string, Value>,       // 非敏感变量
  secretsRef: string[],                   // 敏感变量名（值存 Keychain，不进 Model）
  headers: Record<string, string>,        // 公共 header
  tls: { allowSelfSigned: boolean, caCertRef? }
}
```

**凭据永不进 Model / 永不进事件日志**。子集本来就禁止字符串 Model 字段（NS1024），这条在架构上被强制了；但我们额外要求：**事件日志里出现密钥值时必须替换为占位符**（写时脱敏，见 [08](08-安全基线.md)）。理由：日志是要被导出、分享、归档的，一旦写入就无法收回。

**变量引用语法**：`{{env.baseUrl}}` / `{{var.orderId}}` / `{{secret.apiToken}}`。三类来源分离（环境 / 步骤提取 / 凭据），在编译期校验存在性。

## 4. Run 生命周期

### 4.1 状态机

```
                    ┌──────────┐
        触发 ──────►│ planning │  编译计划；失败 → 直接 plan_failed（不产生 run_event 之外的噪声）
                    └────┬─────┘
                         │ 编译通过
                    ┌────▼─────┐
                    │ running  │◄──── 暂停/恢复（人工介入，见 04 §6）
                    └────┬─────┘
           ┌─────────────┼─────────────┬──────────────┐
           │             │             │              │
      ┌────▼───┐   ┌─────▼────┐  ┌─────▼─────┐  ┌────▼─────┐
      │completed│  │cancelled │  │ errored   │  │ paused→… │
      │（正常） │  │（人取消） │  │（主进程崩）│  └──────────┘
      └────────┘   └──────────┘  └───────────┘
```

**`completed` 不等于"全通过"**：它只表示"跑完了"。通过与否是 verdict 的事（[04](04-结果模型.md)）。这个区分是被测结果可信的基础——"这次运行完成了，其中有 3 个失败"与"这次运行中断了"是完全不同的两件事。

### 4.2 时间与顺序：两个独立的标尺

```
Run {
  id, projectId, planId, envId,
  status, triggeredBy: "human" | "agent" | "schedule" | "retry",
  startedAtMs, finishedAtMs,
  counters: { total, passed, failed, degraded, errored, skipped }
}
```

**每一个事件都带两个标尺**：

1. `seq` —— 严格单调递增的序号（**判定与重放的依据**）
2. `atMs` —— 墙钟毫秒（**展示与统计的依据**）

**为什么必须分开**：如果只用时间戳，同一毫秒内的多个事件顺序不确定（重放会得到不同结果）；如果只用序号，无法计算耗时和展示时间线。这不是洁癖——**判定结果必须可复现**（P4），而可复现的前提是顺序确定。

**耗时的正确算法**：`durationMs` 不用墙钟差，而用 `performance.now()` 的**单调时钟差**（`Date.now()` 会被 NTP 调整影响）。墙钟只用于"这次运行发生在昨天 14:30"这类展示。

### 4.3 计数器是投影，不是真源

`Run.counters` 看起来像状态，实际是**运行结束时算出来并缓存**的。任何时候都可以从事件重算（P2）。

为什么要缓存：列表页要显示几十个 run 的通过率，实时重算每个 run 的全量事件太慢。**但缓存必须可失效、可重算**——提供"重算此运行"操作（重判的一部分，见 04 §5）。

## 5. 执行引擎

### 5.1 HTTP 客户端选型

执行引擎用 **`undici`**（Node 内置，8.x）。它是 Node 官方维护的 HTTP 客户端，能力覆盖测试执行的全部需求：

| 需求 | undici 的支持 |
|---|---|
| 任意大小的请求/响应体 | ✅ 流式处理，无上限（大响应按阈值落 artifact） |
| 任意 header 数量 | ✅ 无限制 |
| 自签证书（内网常见） | ✅ per-request `dispatcher` + `Agent({ connect: { rejectUnauthorized: false } })`，**可按环境单独配置**，无需全局关闭 TLS 校验 |
| 重定向链追踪 | ✅ `redirect: 'manual'` 自行处理，可记录完整链路 |
| 超时控制 | ✅ `headersTimeout` / `bodyTimeout` 分别控制 |
| 连接复用 | ✅ 内置连接池 |
| 响应头全集读取 | ✅ 原生 `Headers` 对象 |
| HTTP/2 | ✅ 支持 |

**为什么不用 Node 内置的 `fetch`**：`fetch` 基于 undici，但**无法按请求指定 dispatcher**——意味着无法为不同环境配置不同的 TLS/代理策略。测试工作台经常需要同时对接多个环境，这个能力是必需的。

**前一版的对比**：前一版因使用 Native SDK 的 `Cmd.fetch`，受限于响应体 256 KiB、请求体 64 KiB、header ≤8 个且 ≤1 KiB、无法自定义 TLS 校验——**完全不足以承载真实 API 测试**，只能把执行引擎挪到 Node 边车。改用 undici 后这个约束消失，执行引擎直接在主进程（[02 §6](02-架构.md#5-worker-池的组织)：HTTP 是 IO 密集，主线程即可）。

### 5.2 单步执行的完整流程

```
PlanEntry 就绪
  → 解析变量模板（env / var / secret）
  → urlguard 检查目标 URL（SSRF 分档，见 08）
  → 构造请求（method / headers / body / timeout / TLS）
  → 发出请求
  → 捕获响应（status / headers / body / 耗时 / 重定向链）
  → 落 artifact（body 超阈值时落文件，库内只存引用）
  → 发出 run_event（step_finished，含观测值）
  → 求值断言（对每个 assert step）
  → 发出 run_event（assert_evaluated，含 actual / expected / passed）
  → 执行 extract（如有）
  → 发出 run_event（var_extracted）
  → 步进到下一个 entry
```

**顺序上的一个关键点**：**先落 artifact、再发事件**。理由：事件一旦提交，UI 就可能显示"某步完成了，点击查看报文"；如果这时 artifact 还没落盘，用户会看到空报文。顺序错了会产生"偶发空数据"这类极难排查的问题。

### 5.3 重试：与 flaky 的正确关系

```yaml
retry:
  maxAttempts: 2         # 总尝试次数（1 = 不重试）
  on: [connect_failed, timed_out, http_5xx]    # 什么情况下重试
  backoff: exponential   # fixed | exponential
  jitter: true           # 抖动，避免同步重试风暴
```

**核心纪律：重试次数不是结果，重试历史才是。**

```
case_result.attempts = 3          # 3 次才成功
case_result.verdict  = "passed"
case_result.flaky    = true       # ★ 关键：一等状态，不是附注
```

**为什么 `flaky` 必须是一等状态**：如果一个用例 3 次里成功 1 次，它的"通过"是没有信息量的——下次可能就失败。把它算作通过会掩盖真实问题；算作失败又会有大量噪声。**正确做法是显式标记为不稳定**，在界面上用独立颜色（紫/橙），在趋势图上单独一条曲线，在模板稳定性报告中单列。

判定规则（见 [04 §3](04-结果模型.md#3-判定模型)）：

| 情况 | verdict | flaky |
|---|---|---|
| 首次通过 | `passed` | false |
| 某次失败后通过 | `passed` | **true** |
| 全部尝试失败 | `failed` | false |
| 重试耗尽且末次是 errored | `errored` | true（如果是间歇性连接问题） |

### 5.4 断言沙箱

`script` 步骤与复杂断言在沙箱执行：

| 项 | 策略 |
|---|---|
| 隔离 | M4 用 `worker_threads` / `vm` isolate；初版可用受限 `vm` |
| 超时 | 默认 5s，硬上限 30s |
| 可用 API | 只读的 `response` / `vars` / 纯计算；**无 `require` / 无 `process` / 无网络 / 无文件** |
| 失败语义 | 抛异常 → 该 assert 判 errored（**不是 failed**——脚本本身坏了不等于被测错了） |
| 可观测 | 记录脚本的返回值与异常栈（截断） |

**"脚本错误算 errored 而非 failed"** 是继 §2.6 之后第二次应用同一条纪律：**把工具的问题算成被测对象的问题，会让报告失真**。

### 5.5 取消与中断

| 触发 | 行为 |
|---|---|
| 用户点"停止" | 设置取消标志；当前 in-flight 请求允许完成（不强行 kill，避免半写状态）；未开始的 entry 标 `skipped`；run → `cancelled` |
| 边车进程崩溃 | IPC 断开检测 → run → `errored(host_crash)`；**已提交事件保留** |
| 主机退出 | 边车随之退出，run → `cancelled(host_exit)` |

**"已提交事件保留"支撑"从此处续跑"**：重启后可以从最后一个成功 entry 继续，而不必从头跑。这是事件日志为真源的直接红利——也是前稿没有的能力。

## 6. 事件流：流程与结果之间的接缝

这一节是本文与 [04](04-结果模型.md) 的接口。

### 6.1 事件类型

执行期发出的事件（**append-only**，永不修改或删除）：

| kind | 何时 | 关键载荷 |
|---|---|---|
| `run_started` | 运行开始 | planId / envId / concurrency / seed |
| `entry_started` | 一个 entry 开始 | entryId / caseId / paramRowLabel |
| `request_sent` | 请求发出 | method / url（**已脱敏**）/ header 名列表 |
| `response_received` | 响应到达 | status / durationMs / bodyRef（artifact 引用） |
| `assert_evaluated` | 每条断言求值 | assertId / severity / expected / actual / passed |
| `var_extracted` | 变量提取 | name / 值（**脱敏后**） |
| `step_errored` | 步骤出错 | reason（封闭枚举）/ detail |
| `entry_finished` | entry 结束 | verdict / durationMs / attempts |
| `retry_scheduled` | 安排重试 | attempt / reason / delayMs |
| `run_finished` | 运行结束 | status / counters |
| `note` | 人工备注 | text（人写的上下文，如"这次是因为发版"） |

**`note` 事件值得单列**：让运行可以被人标注（"环境当时在重启"），这类上下文事后极有价值，且只有人能提供。

### 6.2 为什么"流程"要产出"事件"而不是"结果"

这是本稿最核心的设计判断，值得反复说清：

**如果执行期直接写结果表**，那么：

- 判定规则写死在执行代码里 → 改规则必须重跑 → 历史数据无法用新规则解释
- 中间态无处安放 → UI 只能显示"运行中…"然后突然出结果
- 重试历史丢失 → 只能记最后一次，flaky 无法识别
- 崩溃时进程内的部分结果全丢

**如果执行期只写事件**，那么：

- 判定成为**独立纯函数** → 改规则可对历史重算（re-judge）
- 中间态天然存在 → 实时 UI 免费获得（经 `:live` 查询，见 [05](05-结果呈现.md)）
- 重试全记录 → flaky 可判定
- 崩溃安全 → 已落盘事件就是真实进度

代价是存储更大、需要投影步骤。**这个代价必须付**：测试结果的价值在于可信，而可信来自"每个数字都能被追问到底"。

### 6.3 事件与投影的写入路径

```
runner（主进程）产生事件
  → 攒批（攒 N 条或 T 毫秒，二者先到为准）
  → 单事务写入：事件 + 投影行
  → 提交
     ├─ IPC 推送 runEvents → 界面增量更新（[02 §5](02-架构.md#43-实时推送由页面轮询驱动)、[05 §3](05-结果呈现.md#3-实时刷新机制)）
     └─ artifact 已在事务前落盘（§5.2 的顺序纪律）
```

**攒批参数**（初版建议，可实测调整）：

| 参数 | 值 | 理由 |
|---|---|---|
| 攒批条数 | 32 | 把多次 fsync 合并为一次，是写入吞吐的关键 |
| 攒批间隔 | 100ms | 低于人眼感知阈值（~150ms），界面感觉是实时的 |
| 界面时钟 | 1s | 只驱动耗时秒表类显示，不触发数据查询 |

**"投影行与事件同事务"** 是要点：不能出现"事件写进去了但投影没写"的中间态，否则界面会短暂显示不一致的数据。二者必须原子。

## 7. 流程的可观测性与反馈

### 7.1 实时进度：回答"还要多久"

运行中界面必须能回答三个问题：

1. **完成了多少**：`已完成 entry / 总 entry`（不是用例数——参数化后 entry 数才是真实工作量）
2. **还要多久**：基于已完成 entry 的**中位耗时**外推剩余（不用平均，避免异常值误导）
3. **现在在干什么**：当前 in-flight 的 entry（用例名 + 参数行标签）

外推的实现：`remainingMs = medianDuration(已完成的同类 entry) × 剩余数 / concurrency`。**按 kind 分组取中位**——`db_check` 和 `request` 的耗时量级完全不同，混在一起外推会离谱。

### 7.2 进度是投影，不是计数器

`已完成 entry 数` 不存字段，**从 `case_result` 行数派生**（P2）。这样进度天然准确——不存在"计数器更新漏了一次导致进度卡在 99%"这类经典 bug。

### 7.3 中断点恢复

边界车崩溃后：

```
最后一个 entry_finished 事件 → 已完成的 entry 集合
未完成的 entry → 这些是恢复点
```

UI 提供"从此处续跑"：用**同一个 plan**（`seed` 不变，保证参数化结果一致）+ 跳过已完成的 entry。这要求 plan 是可持久化、可重放的（§3.1 的设计已满足）。

### 7.4 反馈回路：原则的测试价值

运行结束后可以回答一个上游关心的问题：**哪些原则真正在起作用？**

| 指标 | 计算 | 用途 |
|---|---|---|
| 原则触发率 | 引用该原则的用例数 / 总用例数 | 无引用的原则可能是冗余的 |
| 原则违反检出率 | 因该原则派生断言而 failed 的次数 | 高检出 = 该原则有真实价值 |
| 零检出原则 | 从未导致失败的边界原则 | **可疑**：可能约束写错了，也可能测试值没打到位 |
| 无溯源用例 | `provenance` 为空的用例占比 | 越高说明 Agent 在臆测，需人工介入 |

**"零检出原则"是这里最有价值的信号**：一条写着"金额 ≤ 50000"的原则，如果所有测试值都在边界内，说明**边界根本没被测**。这会反向提示 S5 该加强参数化——形成 S6 → S5 → S3 的反馈闭环，而不是单向流水线。

这些指标**全部是查询期派生**（P2），不落聚合表。
