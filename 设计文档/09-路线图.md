# 09 · 路线图与待验证项

> 本文给出里程碑、出口标准，以及**六项必须在动手前实测的未知**。
> 诚实标注未知比画出漂亮的甘特图更有价值——尤其当设计依赖的是尚未实测的外部接口。

## 1. 待验证项（阻断 M1）

技术选型变更后，前一版的 V1–V6 全部失效（它们围绕 Native SDK 的限制）。以下七项是**新版设计所依赖、但尚未实测**的接口。

**M1 的第一个任务不是写业务代码，而是在一天内跑通这七项最小验证。** 每一项都可能改变实现方式，越早发现代价越小。

### W1 · `libfx` 能否在子进程中加载运行（★★ 最高优先级）—— ✅ 已验证（2026-10-01，子进程路径成立）

> **结论**：加载 ✅、`getBackendInfo`→`native` ✅、无效密钥→`stopReason:'refused'` 干净拒绝（非崩溃）✅。
> 真实凭据的流式 + checkpoint 往返待首次配置凭据后补测。详见 [`docs/verification/W1-libfx.md`](../docs/verification/W1-libfx.md)。Agent 层已按 child_process 架构落地（`src/agent/`）。

| 项 | 内容 |
|---|---|
| **未知** | libfx（N-API 原生模块）在独立 Node 子进程中能否正常加载、流式输出、checkpoint 往返？ |
| **为什么重要** | **阻断 Agent 功能**。这是 S5（用例合成）的唯一依赖 |
| **当前假设** | 可加载。子进程就是普通 Node 进程，行为与直接用 Node 无异（比 worker 方案更可预测） |
| **验证方法** | ① 起一个子进程 `require('libfx')` → 调 `getBackendInfo({ surface: 'agent', backend: 'auto' })` 看是否返回 `native`；② 真实跑一轮 `prompt`，确认 `for await` 流式事件到达；③ `agent.checkpoint()` 拿到二进制并写回主进程、再恢复一次 |
| **若假设错误** | 备选顺序：① 改到 core-worker 内加载（N-API 在 worker 的兼容性）；② 试 `backend: 'wasm'`（需 JSPI）；③ 若原生模块完全不可用，退到云端 Agent API（牺牲本地化） |
| **备注** | 优先验证子进程路径——它风险最低，且不受 `show()` 阻塞影响（子进程有独立完整的事件循环） |

### W2 · `ts-morph` 在真实仓库的分析准确率与耗时

| 项 | 内容 |
|---|---|
| **未知** | 对 Express / Fastify / NestJS / Koa 的真实项目，路由提取的准确率与耗时？万级文件仓库是否可接受？ |
| **为什么重要** | **S2 的出口标准（路由提取 ≥90%）**，也是整个"源码驱动"定位能否成立的基础 |
| **当前假设** | 中小仓库（<2k 文件）秒级完成，准确率 >90%；大仓库需配合 `oxc-parser` 初筛 |
| **验证方法** | 选 3–5 个真实开源 TS 服务，跑一遍并人工核对提取结果；记录耗时与误报/漏报 |
| **若准确率不足** | 补充正则兜底（前稿已有此设计）并降低置信度标记；必要时针对具体框架写专用适配器 |

### W3 · `ts-morph` 提取数据约束的实际覆盖率

| 项 | 内容 |
|---|---|
| **未知** | 能提取出多少比例的 zod / joi / class-validator / express-validator / Prisma 约束？跨文件（如 schema 定义在独立模块）能否解析？ |
| **为什么重要** | **S3 的能力边界**——原则提取是"从源码提炼测试数据设计原则"的核心，直接决定合成用例的质量 |
| **当前假设** | 同文件内的链式调用可提取（`z.number().max(50000)`）；跨文件需类型解析，覆盖率下降 |
| **验证方法** | 对含这些库的真实项目实测，统计能提取的原则数 / 源码中实际存在的约束数 |
| **若覆盖率不足** | 明确界面提示"该项目原则提取覆盖率较低，建议人工补充"，而不是静默缺失（[10 §7](10-技术选型.md#8-风险与对策)） |

### W4 · `node:sqlite` 的功能是否够用

| 项 | 内容 |
|---|---|
| **未知** | Node 22+ 内置的 `node:sqlite` 是否支持事务、窗口函数、`user_version`、并发读写？稳定性如何（是否仍标记 experimental）？ |
| **为什么重要** | 决定是否需要引入 `better-sqlite3`（原生模块，带来跨平台编译负担） |
| **当前假设** | 足够。若不足则退到 `better-sqlite3`，API 差异小，封装层可吸收 |
| **验证方法** | 测：BEGIN/COMMIT 事务、`ROW_NUMBER() OVER`、`PRAGMA user_version`、多 worker 并发读、大事务性能 |
| **若不够用** | 用 `better-sqlite3`，并在打包时处理各平台预编译 |

### W5 · 高频 IPC 推送下渲染进程的实际表现

| 项 | 内容 |
|---|---|
| **未知** | 每秒 50–100 次事件写入 + 推送时，渲染进程的帧率、内存、GC 表现？虚拟表格能否跟上？ |
| **为什么重要** | 决定攒批参数（32/100ms 是否合适）与是否需要进一步优化 |
| **当前假设** | 攒批后（每 100ms 一批）完全无压力 |
| **验证方法** | 模拟一次 5000 entry 的运行，用 WebView 的开发者工具（`new Webview(true)`）性能面板测帧率与内存；并实测 SAB 轮询在 100ms 间隔下的 CPU 占用 |
| **若表现不佳** | 加大攒批间隔 / 提高虚拟化参数 / 把聚合计算移到主进程 |

### W6 · 跨平台 WebView 差异（★ 跨平台可行性）

| 项 | 内容 |
|---|---|
| **未知** | 系统 WebView 在三平台的差异：macOS WebKit / Windows WebView2 / Linux GTK-WebKit。CSS 特性、JS 支持、`bind` 行为是否一致？ |
| **为什么重要** | **决定跨平台能否成立**。本机实测只在 macOS 上做过 |
| **当前假设** | macOS 可用（已实测）。Windows WebView2（Chromium 内核）差异较小；Linux 依赖 GTK-WebKit 版本，风险最高 |
| **验证方法** | 在 Windows 与 Linux（至少一个发行版）上跑最小应用：开窗、加载页面、`bind` 双向调用、`eval`、DevTools |
| **若差异过大** | 前期**只支持 macOS**（开发者本机优先），Windows/Linux 延后并在文档中明确标注 |

### W7 · 原生插件能否 CI 预编译随包分发

| 项 | 内容 |
|---|---|
| **未知** | `libwebview.node` 能否在 CI 为各平台/架构预编译，随包分发而不要求用户本地编译？ |
| **为什么重要** | 用户装个测试工具不该先装 cmake + Xcode |
| **当前假设** | 可以。实测本机编译仅 10 秒，且插件只依赖系统框架（`otool -L` 已确认） |
| **验证方法** | 在 GitHub Actions 三平台各跑一次 `npm install webview-nodejs`，打包产物并验证可加载 |
| **若不可行** | 要求用户安装编译工具（体验降级），或改用纯 JS 的替代方案（若有） |

### 验证任务的产出物

每项验证产出一个 **`docs/verification/Wn-*.md`**，包含：实测命令、观察结果、与假设的差异、对设计的影响。**这六份文档是 M1 动工前的验收物。**

**W1 应当第一个做**，因为它决定 Agent 的运行方式（子进程 / worker / 云端），越早发现越好。

## 3. 依赖与顺序

```
M0 设计
 │
 ├─► W1..W7 验证（一天）            ← 必须先做（W1 优先单独做）
 │        │
 │        └──► 结论可能微调 M1 实现方式
 │
 └─► M1 骨架 ──► M2 原则 ──► M3 采样
                    │           │
                    └─────┬─────┘
                          ▼
                    M4 执行+结果 ◄── 核心价值在此
                          │
                          ▼
                    M5 Agent 协同
                          │
                          ▼
                    M6 分发
```

**M2 与 M3 可并行**（原则提取与数据库采样无依赖，都只依赖 M1 的项目域）。

**M4 依赖 M2 和 M3**：用例合成需要原则（定边界）和样本（定形态）。但 **M4 的判定/事件核心可以先做**——用人工写的固定用例验证事件日志与判定纯函数，不必等 Agent 就绪。这是推荐的推进方式：**先把结果模型跑通，再接入 Agent**。

## 4. 风险登记

| # | 风险 | 概率 | 影响 | 缓解 |
|---|---|---|---|---|
| R1 | **W1 失败：libfx 原生模块无法加载** | 低 | 中 | 依次退：worker 内加载 → `backend: 'wasm'` → 云端 Agent API；Agent 是独立模块，其余不受影响（[10 §3.3](10-技术选型.md#33-libfx-必须在-worker-或子进程中-待验证-w1)） |
| R2 | **ts-morph 分析准确率或耗时不足** | 中 | **高** | `oxc-parser` 初筛 + 正则兜底 + 专用适配器；界面明示置信度（[10 §7](10-技术选型.md#8-风险与对策)） |
| R3 | **纯 JS 项目类型信息缺失** | 中 | 中 | 降级到语法级分析，置信度标低并**在界面明确提示**（[10 §7](10-技术选型.md#8-风险与对策)） |
| R4 | 大仓库索引慢 | 中 | 中 | worker 池并行 + 限定目录范围 + 快速模式（W6 验证） |
| R5 | 脱敏与续跑冲突导致续跑能力受限 | **高** | 低 | 已明确选择"脱敏优先"并显式告知（[08 §4.3](08-安全基线.md#43-脱敏的两个特例)） |
| R6 | **跨平台 WebView 差异导致 Windows/Linux 不可用** | **高** | 中 | 前期只支持 macOS；W6 实测定结论；必要时回退到捆绑 Chromium（体积换一致性） |
| R10 | **上游 `webview` 库停止维护** | 中 | 中 | 自写 N-API 绑定（库很薄，约数百行）；或用 `webview_deno` 的 C 层 |
| R11 | 自写更新器不可靠 | 中 | 中 | 初版只做"检查新版本 + 提示下载"，不做静默替换 |
| R12 | 无浏览器级 E2E 导致界面回归漏检 | 中 | 低 | 前端组件测试 + RPC 契约测试补位（[02 §9](02-架构.md#9-测试策略)） |
| R7 | 参数矩阵爆炸拖慢运行 | 中 | 低 | `maxRows` 硬上限 + 拒绝编译（[03 §3.1](03-测试流程.md#31-plan-是编译产物)） |
| R8 | 高频推送导致渲染卡顿 | 中 | 低 | 攒批 32/100ms + 虚拟化（W5 验证） |
| R9 | checkpoint 大小上限 | 中 | 中 | 会话轮转策略（[07 §4.1](07-Agent与人机门.md#41-checkpoint-的归属与流转)） |

**R2 值得单独强调**：**源码分析的准确率是本产品的命门**。如果 ts-morph 只能提取出 50% 的路由，那"源码驱动"就名不副实。这也是 W2/W3 被列为一等验证项的原因——**它们是产品成立性的检验，不只是技术验证**。

**R3 的诚实标注很重要**：本产品假设"源码是 TS 优先"。纯 JS 项目缺少类型信息，原则提取能力会显著下降。**必须在界面上明确标注**（"此项目为纯 JS，原则提取置信度较低"），而不是静默降级让用户以为一切正常。

## 5. 明确不做的事

避免范围蔓延，明确列出**本设计不做**：

| 不做 | 理由 |
|---|---|
| GraphQL / gRPC 测试 | 需要不同的适配器体系；M1–M6 先做 HTTP/REST |
| 性能压测（负载测试） | 定位是功能测试；压测需要不同的引擎与指标体系 |
~~| 浏览器 E2E / UI 测试 | 完全不同的问题域 |~~
| ~~浏览器 E2E / UI 测试~~ | **范围变更（ADR-1，引擎层新增）**：UI 测试以「UI 步骤族 + 驱动抽象」进入引擎层——用例仍是步骤树，`ui_see` 产出 `assert_evaluated`，判定/事件日志/flaky/人机门全部复用，不另起产品。浏览器驱动为可选依赖（playwright-core + 系统 Chrome，不捆绑浏览器，与体积决策一致）。E2E 自动化协议仍不做（系统 WebView 无标准协议的原判断不变）；PRD 作为输入源一并加入（`src/prd/`，确定性解析 + file:line 溯源，prose 需求留给 Agent） |
| 测试用例的版本控制 / Git 集成 | 用例存在 SQLite；导出即可入版本控制，不需要内置 VCS |
| 多用户 / 团队协作 / 服务端同步 | 定位是本地桌面工具 |
| 云执行 / 分布式 runner | 同上 |
| CI 集成（作为 M1–M6 范围） | 导出报告可喂给 CI，但不做 CI 插件；列入"将来" |
| 契约测试（consumer-driven） | 与 Pact 等工具的定位重叠，非本产品核心 |
| 对被测源码的修改能力 | **只读源码**（S1 接入即只读）——这是产品的基本纪律 |

**"只读源码"值得强调**：deepAutoTest 永远不修改被测仓库。这既是安全考量，也是信任基础——用户可以放心把它指向任何仓库。

## 7. 设计自检

最后，回答"这个设计是否忠于它自己声明的原则"：

| 原则 | 本设计的兑现 | 可验证性 |
|---|---|---|
| P1 唯一事实源 | 事件日志为真源；结果表是投影（[04 §1](04-结果模型.md#1-三层分离)） | 投影重建测试（M1 出口标准 ④） |
| P2 派生不存储 | 通过率/趋势/不稳定榜全部查询期算（[06 §3](06-数据模型.md#3-命名查询清单)） | 审查：无聚合表 |
| P3 改变真相必须过门 | 三类对象状态机 + diff 留痕（[07 §5](07-Agent与人机门.md#5-人机协同状态机)） | 单测：AI 无法直接产出 adopted |
| P4 一切可回放、可重判 | 事件 append-only + 判定纯函数 + 重判（[04 §5](04-结果模型.md#5-重判re-judge让结论可以进化)） | 判定穷举单测 + 重判 preview |
| P5 项目即边界 | pid 为会话常量 + `ProjectScope` 首参（[07 §3.2](07-Agent与人机门.md#32-越权防护的实现层次)） | 越权模拟测试 |

**以及三条贯穿性的结果可信纪律**（本稿相对前稿最重要的补充）：

1. `failed` 与 `errored` 严格区分——不把"没测成"算成"被测错了"
2. `degraded` 作为中间态——保护通过率这个数字的可信度
3. `flaky` 是一等标记——不把不稳定伪装成通过

**这三条是测试工具的生命线**：一旦报告开始说谎，工具就会失去信任，然后被绕过。
